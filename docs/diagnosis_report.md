# AlphaFold 3 배치 속도 진단 리포트

작성: 2026-08-19
대상: VHH/나노바디 약 130 aa, 2000건 스크리닝 (RTX 5090 32GB, Docker 이미지 `alphafold3`)
검증 호스트: RTX 5070 Ti 16GB, 24 CPU, RAM 126GB, AF3 commit `97d20234` (v3.0.4-15-g97d2023)

---

## 0. 세 줄 요약

1. **코드 문제다.** 건당 341초 중 구조 예측 자체(GPU 추론)는 약 4~5초다. 나머지는
   JSON마다 컨테이너를 새로 띄우는 데 드는 고정 비용이다. 단일 프로세스로 바꾸면
   GPU 단계는 건당 31.95초 → 5.39초(5.93배, 실측)가 된다.
2. **그런데 코드를 고치면 병목이 MSA(CPU)로 옮겨간다.** 2000건 약 40시간 중 **MSA가 37시간(93%)**
   이고, 이것은 프로세스를 몇 개로 쪼개도 줄지 않는다. 다음 레버는 코드가 아니라
   MSA 자체를 줄이는 것이다.
3. **기존 760건은 폐기하지 않아도 된다.** 축소 DB는 MSA 깊이를 818~1,186배 얕게 만들지만,
   VHH 단량체 신뢰도는 거의 변하지 않았다(ranking score 6건 중 무변화 3, +0.03 두 건,
   -0.01 한 건). **단 항원-나노바디 복합체는 측정하지 않았고, 그쪽은 전체 DB가
   사실상 필수로 보인다.**

이 리포트의 모든 수치에는 출처를 붙였다. **[직접측정]** 은 이 과제에서 실제로 잰 값,
**[인용]** 은 다른 트랙이 측정해 이 리포트가 옮긴 값, **[추정]** 은 계산으로 환산한 값,
**[미측정]** 은 재지 않았으므로 근거가 없는 항목이다.

## 질문 1. 코드 문제인가, AF3가 원래 느린가

### 답: 코드 문제다. 다만 코드를 고치면 병목이 MSA로 옮겨간다.

건당 341초를 단계별로 갈라 보면 이렇게 된다.

| 단계 | 시간 | 출처 |
|---|---|---|
| 순수 GPU 추론 (컴파일 끝난 뒤, sample 5 × recycle 10, 130 aa) | **4.20초** | [직접측정] |
| 특징화(featurisation) | 0.55초 | [직접측정] |
| MSA 검색 (축소 DB 4종) | 약 3초 | [인용] |
| 프로세스 기동 (컨테이너 + JAX/CUDA 초기화 + 가중치 1.15GB 로딩) | **9.1~9.2초** | [직접측정] |
| 첫 등장 버킷의 XLA 컴파일 | 약 15~25초 (해당 건에만) | [직접측정] |

즉 **AF3가 실제로 계산하는 데 쓰는 시간은 건당 8초 안쪽**이다.
연구자 방식이 341초가 되는 이유는 이 8초 앞뒤로 붙는 고정 비용을 **2000번 다시 내기**
때문이다.

### 실측 A/B — 두 요인을 분리했다

32건 × 3반복, 중앙값, MSA 없는 GPU 추론 경로만 격리, 조건 순서를 반복마다 회전.
**[직접측정]**

| 방식 | 캐시 디렉터리 | 건당 | 3회 값 | 추론/건 | 기동/건 |
|---|---|---|---|---|---|
| 프로세스별 (현재 방식) | 미지정 | **31.95초** | 31.84 / 31.95 / 31.98 | 21.71 | 9.19 |
| 프로세스별 | 지정 | 18.13초 | 18.13 / 18.13 / 18.13 | 7.96 | 9.12 |
| 단일 프로세스 | 미지정 | 6.26초 | 6.25 / 6.26 / 6.28 | 5.26 | 0.44 |
| 단일 프로세스 (권장) | 지정 | **5.39초** | 5.39 / 5.39 / 5.41 | 4.40 | 0.44 |

반복 간 편차가 0.1% 수준이다. 측정 중 호스트 load1 은 1.1~2.9 로 통제했다.

| 개입 | 개선 배수 |
|---|---|
| **단일 프로세스화** (캐시 미지정 상태에서) | **5.10배** |
| 단일 프로세스화 (캐시 지정 상태에서) | 3.36배 |
| 캐시 디렉터리 지정만 (프로세스별 유지) | 1.76배 |
| 캐시 디렉터리 지정만 (단일 프로세스에서) | 1.16배 |
| **최악 → 최선** | **5.93배** |

**주효과는 단일 프로세스화다.** `--jax_compilation_cache_dir` 한 줄만 추가하는 쉬운 처방으로는
1.76배(전체 5.93배 중 30%)밖에 얻지 못한다. 게다가 이 1.76배도 배치가 커지면 사라진다 —
캐시가 없애는 것은 **첫 2건의 컴파일뿐**이기 때문이다. 96건 순회에서 확인했다:

| | 1번째 | 2번째 | 3번째~ (정상 상태) |
|---|---|---|---|
| 캐시 지정 | 7.95초 | 6.87초 | **4.20초** |
| 캐시 미지정 | 21.90초 | 20.62초 | **4.20초** |

정상 상태 4.20초는 캐시 여부와 완전히 무관하다. 96건에서 캐시가 절약한 총량은 약 28초,
건당 0.3초다. **2000건에서는 0에 수렴한다.** 그래도 한 줄이니 붙여 두면 된다 —
작업을 쪼개야 하는 상황(중간에 멈췄다 다시 시작 등)에서는 1.76배가 실제로 온다.

### "AF3가 원래 느린가"에 대한 답

AF3의 GPU 추론은 130 aa 단량체에서 4.2초다. 느리지 않다.
**느린 것은 AF3의 준비 과정(가중치 로딩, XLA 컴파일)이고, 그것은 원래 한 번만 내면 되는
비용이다.** 연구자 스크립트가 그것을 2000번 내게 만든 것이 원인이다.

### 그러나 — 코드를 고친 뒤에는 MSA가 병목이다

여기가 이 리포트에서 가장 중요한 부분이다. 위 5.93배는 **GPU 단계만**의 이야기다.

| 단계 | 건당 | 2000건 | 출처 |
|---|---|---|---|
| GPU: 현재 방식 | 31.95초 | 17.8시간 | [직접측정] |
| GPU: 단일 프로세스 + 캐시 | 5.39초 | **3.0시간** | [직접측정] |
| MSA: 최대 처리율 0.895 타깃/분 | 67.0초 | **37.2시간** | [인용] |
| **합계 (권장 구성)** | 72.4초 | **40.2시간 (1.7일)** | [추정, 합산] |

**2000건 40시간 중 37시간이 MSA다 — 전체의 93%.**
GPU 단계를 3시간에서 0시간으로 만들어도 총 시간은 40시간에서 37시간이 된다.

그리고 MSA는 **더 병렬화해서 줄일 수 없다.** 14개 조합 스윕 **[인용]**:

| 총 요구 스레드 | 최고 처리율 (타깃/분) |
|---|---|
| 4 | 0.195 |
| 8 | 0.374 |
| 16 | 0.673 |
| 24 | 0.778 |
| 32 | **0.890** |
| 48 | **0.895** |
| 96 | 0.848 (감소) |

24코어 호스트에서 32~48스레드에서 포화하고, 96스레드에서는 오히려 떨어진다.
그리고 **스레드 총량이 같으면 동시 실행 갈래를 늘리는 쪽이 손해**다
(32스레드를 1갈래에 몰면 0.890, 2갈래로 쪼개면 0.767).
이유는 명확하다 — AF3는 이미 체인 1개당 DB 4개를 `ThreadPoolExecutor(max_workers=4)` 로
동시 검색한다. **병렬성이 이미 코드 안에 있다.**

포화의 원인이 CPU인지 디스크 I/O인지는 **[미측정]** 이다.
포화점이 코어 수 근방이고 과다구독에서 하락하는 형태는 CPU 포화의 전형적 패턴이지만,
디스크 읽기량을 직접 계측하지 않았으므로 단정할 수 없다.

### 질문 1 정리

- 코드 문제다. 건당 341초의 대부분은 예측이 아니라 프로세스 재기동 비용이다.
- 고치면 GPU 단계는 5.93배 빨라진다 **[직접측정]**.
- 전체 파이프라인 기준으로는 189시간 → 24~40시간, **4.7~7.9배** **[추정]**.
  범위의 하단은 MSA 37시간을 더한 합산, 상단은 축소 DB end-to-end 실측(24.1시간) 기준이다.
- **"341초 ÷ 5.39초 = 63배" 같은 계산은 쓰지 말 것.** 341초에는 MSA가 들어 있고
  5.39초에는 없으므로 같은 것을 비교하지 않는다.

## 질문 2. 여러 개를 동시에 돌리려면 무엇이 필요한가

### 답: 메모리는 이미 충분하다. 그러나 다중화는 잘못된 방향이고, 진짜 레버는 MSA 사전계산이다.

### (a) "GPU 메모리가 꽉 차서 하나밖에 못 돌린다"는 전제는 틀렸다

| 조건 | 최대 VRAM | 출처 |
|---|---|---|
| 선점 ON (공식 Dockerfile 기본값) | 15,157 MiB | [인용] |
| 선점 OFF, 18런 전체 | **2,942~2,963 MiB** | [직접측정] |
| 선점 OFF (이전 측정, 호스트 고부하 중) | 5,291 MiB | [인용] |

`nvidia-smi` 가 15GB를 쓰는 것처럼 보이는 것은 **JAX가 미리 잡아둔 예약(선점)** 이고,
실제 수요가 아니다. 선점을 끄면 이번 18런 전체에서 피크가 약 2.9~3.0 GB였다.
이전 측정의 5,291 MiB 와 차이가 나는 원인은 규명하지 못했다 **[미측정]**.
보수적으로 **3~5.3 GB** 로 보면 된다. 어느 값이든 32GB 카드에는 여유가 크다.

선점을 끄는 방법 (docker `-e` 로):
```
-e XLA_PYTHON_CLIENT_PREALLOCATE=false
```

### (b) 그런데 여러 프로세스를 띄우는 것은 **잘못된 방향**이다

메모리가 남으니 프로세스를 4개 띄우면 4배 빨라질 것 같지만, 실측은 반대를 말한다.

- 프로세스를 하나 더 띄울 때마다 **기동 비용 9.1~9.2초를 다시 낸다** **[직접측정]**.
  이 비용은 캐시 디렉터리를 지정해도 줄지 않는다(캐시는 컴파일을 없애지 기동을 없애지 않는다).
- 단일 프로세스에서는 같은 비용이 0.44초/건으로 상환된다.
- GPU 자체는 하나이므로, 프로세스를 늘려도 계산 자원이 늘지 않는다.
  늘어나는 것은 컨텍스트 스위칭과 메모리 대역폭 경쟁뿐이다.

즉 **"동시에 여러 개"의 정답은 프로세스를 늘리는 것이 아니라 프로세스 하나가 여러 건을
순회하게 만드는 것**이다. 그것이 `--input_dir` 이고, 5.10배의 출처다.

MSA 쪽도 같다. 갈래를 늘리는 것은 스레드 총량이 같으면 오히려 느리다 **[인용]**.

### (c) 그러면 실제로 해야 하는 것

MSA와 GPU는 서로 다른 자원(CPU 대 GPU)을 쓰므로, **이 둘을 겹치는 것**은 의미가 있다.
2단계 분리(`--norun_inference` 로 MSA만 → `--norun_data_pipeline` 로 추론만)가 그것을 가능하게 한다.

다만 겹치기의 실질 처리율은 **[미측정]** 이다. 이론적 하한은 max(37.2, 3.0) = **37.2시간**,
상한(겹치지 않을 때)은 40.2시간이다. 겹쳐서 얻을 수 있는 최대 이득은 3시간(7%)이다.

**진짜 레버는 MSA 자체를 줄이는 것이다.** 우선순위 순으로:

1. **MSA를 한 번 만들어 보관하고 재사용한다.** MSA 단계 산출물 `*_data.json` 에는
   MSA가 그대로 담겨 있다. 시드를 늘리거나, 샘플 수를 바꾸거나, 리간드를 붙여 다시
   돌릴 때 `--norun_data_pipeline` 으로 MSA 재계산을 건너뛸 수 있다.
   같은 서열을 두 번 이상 돌릴 계획이 있다면 이것이 가장 큰 절약이다.
2. **서열이 비슷한 것끼리 MSA를 공유할 수 있는지 검토한다.**
   VHH 프레임워크는 거의 동일하고 CDR만 다르므로 이론적으로 여지가 있으나,
   AF3가 MSA를 서열 단위로 요구하므로 그대로는 안 된다. **[미측정, 미검증 아이디어]**
3. **축소 DB를 유지한다.** 이미 그렇게 하고 있고, 이것이 MSA 37시간을 유지하는 이유다
   (전체 DB면 건당 30.5분 = 2000건 42일이다). 품질 영향은 아래 4절 참고.
4. **파이프라인 겹치기.** MSA 배치를 먼저 돌려 놓고, 쌓이는 대로 추론을 돌린다.
   최대 이득 7% **[미측정]**.

### 질문 2 정리

- 메모리는 충분하다(실측 3~5.3GB / 32GB). `nvidia-smi` 의 15GB는 예약이지 수요가 아니다.
- 그러나 프로세스를 늘리면 기동 비용 9.1초를 그만큼 다시 낸다. **다중화는 잘못된 방향이다.**
- 올바른 답은 프로세스 1개 + `--input_dir` 순회다.
- 그 다음 레버는 MSA 사전계산·재사용이다. 이것이 2000건 40시간의 93%를 건드리는
  유일한 수단이다.

## 질문 3. 파이썬 스크립트 없이 돌리는 간단한 명령이 있는가

### 답: 있다. `--json_path` 를 `--input_dir` 로 바꾸는 것 하나다.

이 한 줄이 5.10배의 전부다. 지금 쓰는 명령에서 바꿀 것은 두 곳이다.

```bash
docker run --rm --gpus all \
  -e XLA_PYTHON_CLIENT_PREALLOCATE=false \
  -v $HOME/public_databases:/root/public_databases \
  -v $HOME/af3_models:/root/af3_models \
  -v $PWD/vhh_001_in:/root/af3_in \
  -v $PWD/vhh_001_out:/root/af3_out \
  -v $HOME/af3_jax_cache:/root/af3_cache \
  alphafold3 \
  python run_alphafold.py \
    --input_dir=/root/af3_in \
    --model_dir=/root/af3_models \
    --db_dir=/root/public_databases \
    --output_dir=/root/af3_out \
    --jax_compilation_cache_dir=/root/af3_cache \
    --buckets=128,256 \
    --jackhmmer_n_cpu=8 \
    --nhmmer_n_cpu=8
```

바뀐 것:
- `--json_path=<파일 하나>` → **`--input_dir=<폴더>`** — 이것이 본질이다.
  루프를 셸에서 돌리는 대신 AF3 안에서 돌게 만든다.
- `--buckets=128,256` — VHH 111~144 aa 에 필요한 계단만 남긴다.
  **`128` 을 빠뜨리면 안 된다** (아래 함정 참고).

`--jax_compilation_cache_dir` 는 넣어도 손해가 없으니 넣는다(단일 프로세스에서 이득은 1.16배).
`XLA_PYTHON_CLIENT_PREALLOCATE=false` 는 속도가 아니라 GPU를 다른 작업과 공유하기 위한 것이다.

**주의할 함정: 버킷 사다리는 128부터 시작한다.**
`run_alphafold.py` 의 기본 버킷은 `128, 256, 384, 512, ...` 다.
VHH 111~144 aa 중 128 토큰 이하인 것은 128 버킷에, 그보다 긴 것은 256 버킷에 들어간다.
정상 상태 추론 시간이 **버킷 128 은 4.20초, 버킷 256 은 9.44초 — 2.25배 차이**다
**[직접측정]**. `--buckets=256` 만 주면 111 aa 서열도 256으로 패딩되어 2배 이상 느려진다.

더 편한 방식(래퍼 스크립트)도 함께 준다. 재시작·재시도·집계까지 붙어 있다:
```bash
bash af3run.sh vhh_001 dry        # 실행 없이 명령만 확인
bash af3run.sh vhh_001 screen     # 전수 경량 스크리닝
bash af3run.sh vhh_001 collect    # 결과를 CSV 한 장으로
```
자세한 것은 `docs/operations_guide.md` 와 `docs/commands.md` 참고.

## 4. 추가 발견 — 축소 DB는 이 배치에서 품질을 거의 깎지 않았다

연구자가 쓰고 있는 축소 DB(약 2GB)는 전체 DB(850GB)와 비교하면 극단적으로 얕다.
AF3 파이프라인을 두 조건으로 전량 돌려 비교했다 (VHH 단량체 6종) **[인용]**.

| 타깃 | unpaired MSA 깊이 (축소→전체) | 배수 | ranking (축소→전체) | Δ | pLDDT평균 | Δ |
|---|---|---|---|---|---|---|
| 7DJX_1 | 10 → 10,691 | 1,069배 | 0.82 → 0.82 | 0.00 | 82.6 → 82.8 | +0.2 |
| 7A50_1 | 9 → 10,677 | 1,186배 | 0.85 → 0.88 | **+0.03** | 84.1 → 86.2 | +2.1 |
| 8V8K_1 | 12 → 10,745 | 895배 | 0.85 → 0.88 | **+0.03** | 88.2 → 89.9 | +1.7 |
| 4QGY_1 | 9 → 10,671 | 1,186배 | 0.87 → 0.86 | -0.01 | 88.0 → 87.0 | -1.0 |
| 4S11_1 | 13 → 10,666 | 820배 | 0.88 → 0.88 | 0.00 | 90.0 → 90.4 | +0.4 |
| 7MFV_1 | 13 → 10,640 | 818배 | 0.90 → 0.90 | 0.00 | 92.3 → 92.7 | +0.4 |

paired MSA 깊이는 158~225 → 24,250~27,353 으로 **120~150배** 차이다.
시간 대가는 건당 43.3초 → 1,830초(30.5분), **42.2배**다.

### 무엇을 읽어야 하나

**MSA 깊이가 1,000배 차이나는데 신뢰도는 거의 같다.**
ranking score 변화는 -0.01 ~ +0.03이고 6건 중 3건은 완전히 동일했다.
하락한 -0.01 은 같은 케이스 내 5개 샘플의 ranking 산포(0.002~0.008) 범위 안이므로
의미 있는 하락이 아니다. 실질적 개선은 +0.03 두 건뿐이고, 이는 스크리닝 순위를
뒤집을 크기가 아니다.

이유는 VHH의 성질에 있다. 면역글로불린 폴드가 극도로 보존되어 있고, PDB에 템플릿이
수천 개 있으며(템플릿 검색은 두 조건 모두 전체 DB를 썼다), 길이가 130 aa 내외로 짧다.
AF3는 얕은 MSA에서도 템플릿과 학습된 폴드 지식으로 프레임워크를 복원한다.
**MSA 깊이가 결정적인 것은 신규 폴드와 다중체 계면인데, 이 배치는 둘 다 아니다.**

### 기존 760건에 대한 판단

**폐기 대상이 아니다. 전수 재실행도 권하지 않는다** — 2000건을 전체 DB로 돌리면
42일이 걸린다 **[인용, 실측 환산]**.

권장:
- 전수 스크리닝은 축소 DB 유지. 단 단일 프로세스로 전환.
- **최종 후보로 좁혀진 소수(수십 건 규모)만 전체 DB로 재실행.**
  목적은 점수를 올리는 것이 아니라(개선이 확인되지 않았다) **"얕은 MSA가 원인이
  아님을 확인하는 것"** 이다. 후속 실험에 들어갈 후보라면 30분/건의 값어치가 있다.

한 가지 짚어 둘 것: **"점수가 낮은 건일수록 전체 DB에서 개선된다"는 가설은
이 데이터로 지지되지 않는다.** 개선된 2건은 축소 DB에서 둘 다 0.85였고,
**가장 낮았던 7DJX(0.82)는 전혀 개선되지 않았다.** 상관계수는 r = -0.33 (n=6) 으로
통계적으로 무의미하다. 따라서 "낮은 점수 건만 재실행" 규칙을 이 측정으로 정당화할 수 없다.

### 반드시 함께 읽어야 하는 미측정 위험 2가지

**(a) CDR 루프의 잔기별 민감도를 분해하지 않았다** **[미측정]**
위 pLDDT 값은 원자 pLDDT의 평균이고, VHH에서 원자 대부분은 프레임워크에 속한다.
**즉 이 지표는 구조적으로 프레임워크가 지배한다.** CDR3처럼 서열이 다양한 영역은
MSA 깊이에 더 민감할 수 있는데, 잔기별로 나눠 보지 않았다.
항원 결합 부위 구조가 중요한 용도라면 이 부분은 열린 위험으로 남는다.
(참고: `af3_collect.py` 는 `*_confidences.json` 의 원자별 pLDDT를 읽으므로,
CDR 구간의 잔기 번호를 알면 그 구간만 따로 평균 낼 수 있다. 이번에는 하지 않았다.)

**(b) 항원-나노바디 복합체의 계면 신뢰도는 측정하지 못했다** **[미측정]**
비교한 6종은 모두 단량체라 ipTM(계면 신뢰도)이 산출되지 않았다.
그런데 **paired MSA 깊이가 120~150배 차이난다** — paired MSA는 복합체 계면 예측에
직접 쓰이는 정보다. 따라서 복합체 예측 단계에서는 축소 DB가 문제가 될 가능성이
상당하고, **전체 DB가 사실상 필수로 보인다. 다만 이것은 추론이며 측정하지 않았다.**
복합체로 넘어갈 계획이 있으면 소수(예: 10건)로 축소/전체 대조를 먼저 하는 것이 안전하다.

## 5. 2단계 전략(경량 스크리닝 → 상위 재실행)에 대한 정직한 이야기

권장 전략은 이렇다:
1. 2000건 전수를 경량 설정(`--num_diffusion_samples=1 --num_recycles=3`)으로 스크리닝
2. 상위 후보만 AF3 기본값(sample 5 × recycle 10)으로 재실행

**그러나 이 전략의 핵심 가정 — "경량 설정의 순위가 기본값의 순위를 보존한다" — 는
측정하지 못했다** **[미측정]**.
Spearman 상관, 상위 N 회수율, 권장 컷오프 값 모두 **수치 근거가 없다.**

따라서:
- 전략 자체는 권장한다(비용 구조상 합리적이다).
- **그러나 컷오프는 우리가 정해 줄 수 없다.** 소규모 예비실험으로 직접 정해야 한다.
  방법: 무작위 30~50건을 골라 경량과 기본값 양쪽으로 돌리고, 두 순위를 비교한다.
  경량에서 상위 20%였던 것 중 몇 %가 기본값에서도 상위 20%인지 세면 그것이 회수율이다.
  회수율이 낮으면 컷오프를 넉넉히 잡아야 한다(예: 상위 30%를 재실행).
- 이 예비실험 자체의 비용은 작다. 경량 설정에서 건당 몇 초이므로 50건 왕복은
  수십 분 규모다.

`af3_collect.py --top N --top-by <지표>` 가 후보 목록과 그 컷오프 값을 뽑아 준다.
다만 그 컷오프는 "N건을 골랐을 때의 경계값"을 보고하는 것이지 **추천값이 아니다.**

## 6. 처방 요약 (우선순위 순, 근거 배수 포함)

| 순위 | 처방 | 실측 이득 | 근거 |
|---|---|---|---|
| 1 | `--json_path` → **`--input_dir`** 단일 프로세스 순회 | **5.10배** | [직접측정] |
| 2 | `--buckets` 에 **128 을 포함** | 최대 2.25배 (128에 들어가는 건에 대해) | [직접측정] |
| 3 | `--jax_compilation_cache_dir` 지정 | 1.16배 (단일 프로세스), 1.76배 (프로세스별) | [직접측정] |
| 4 | MSA 는 `--jackhmmer_n_cpu = min(코어수/2, 8)`, **갈래 1개** | 갈래 늘리면 오히려 손해 | [인용] |
| 5 | `XLA_PYTHON_CLIENT_PREALLOCATE=false` | 속도 이득 아님. GPU 공유 목적 | [직접측정] |
| 6 | 길이순 정렬 | **0.00초/건** | [직접측정] |
| 7 | **MSA 사전계산·재사용** | 40시간의 93%를 건드리는 유일한 레버 | [추정] |

6번을 특별히 적어 둔다. 인계받은 가정은 "정렬하지 않으면 버킷이 오가며 재컴파일이
반복된다"였는데, **실측이 이를 뒤집었다.** 버킷 128/256을 11회 왕복한 조건과 1회 전환
조건의 건당 시간이 **둘 다 9.11초로 동일**했다. XLA는 버킷별 컴파일 결과를 프로세스
수명 동안 보유하므로, 컴파일은 각 버킷의 **첫 등장에서만** 일어난다.
정렬은 넣어도 손해가 없으니 스크립트에 남겨 두었지만, 우선순위 높은 처방으로 제시하면
과장이 된다.

## 7. 이 리포트가 측정하지 못한 것 (전체 목록)

근거 없이 채우지 않았다. 아래는 모두 **[미측정]** 이다.

1. **MSA 처리율을 이 트랙이 직접 재측정하지 않았다.** 0.895 타깃/분은 다른 트랙의
   14조합 스윕 인용값이다. 포화 원인(CPU 대 디스크 I/O)도 규명하지 못했다.
2. **MSA/추론 파이프라인 중첩 시의 실질 처리율.** GPU가 굶는지 여부 미확인.
3. **경량 설정의 순위 보존.** 5절 참고. 컷오프 근거가 없다.
4. **16GB 카드의 토큰 상한.** unified memory 계열 설정의 실제 동작 여부도 미확인.
5. **콜드 상태 재현.** sudo 없이 페이지 캐시를 비울 수 없어, 모든 값은 웜 캐시 기준이다.
   첫 실행은 이보다 느리다.
6. **Docker 대 네이티브 차이.** 검증 호스트에 Docker가 없어 conda 네이티브로 설치했다.
   따라서 우리 31.95초에는 컨테이너 기동 비용이 빠져 있고, **연구자 실제값의 하한**이다.
   즉 실제 개선 배수는 이 계산보다 클 수 있다.
7. **5070 Ti(16GB) 대 5090(32GB) 차이.** 5090이 더 빠르므로 절대 시간은 연구자 쪽이
   짧아질 것이다(추정). 개선 배수는 양쪽에 같은 방향으로 작용해 비교적 안정적일 것이다.
8. **VRAM 2.9GB 대 5.3GB 의 차이 원인.**
9. **CDR 루프의 잔기별 MSA 민감도** (4절 (a)).
10. **복합체 계면(ipTM)에 대한 축소 DB 영향** (4절 (b)).

## 8. 라이선스와 인용 의무 (반드시 확인할 것)

- AF3 **코드는 Apache 2.0** 이지만 **가중치(`af3.bin`)는 별도 약관**이다.
- **비영리 목적으로만 사용 가능**하고 **재배포가 금지**된다.
- AF3 출력물로 다른 구조 예측 모델을 학습시키는 것이 금지된다.
- 논문 등에 사용하면 **Abramson et al. (2024) 인용이 의무**다.
- 약관은 "구글로부터 **직접** 받은 경우"만 사용을 허용한다.
  따라서 가중치를 다른 경로로 받았다면, **공식 접근 요청 절차를 통해 승인 기록을
  남기는 것이 안전하다.**
- 각 결과 폴더에 AF3가 `TERMS_OF_USE.md` 를 함께 써 넣는다. 결과를 공유할 때
  이 파일을 지우지 말 것.

상세는 `docs/license_notes.md` 참고.
