# MSA 시간 주장 정정 기록

작성 목적: 이 저장소가 자기 측정 조건을 정직하게 말하게 만드는 것. 같은 혼동이
다시 생기지 않게 하려고 무엇이 틀렸고 어느 원자료를 근거로 무엇을 고쳤는지 남긴다.

정본은 `docs/two_stage_notes.md` 3절이다. 이 문서와 저장소의 다른 문서는 모두
그 문서에 맞춰 정리했다.

---

## 1. 무엇이 틀렸나

저장소 여러 곳이 이렇게 적고 있었다.

> 2000건 40.2시간 중 MSA 가 37.2시간(93%). MSA 처리율 0.895 타깃/분, 건당 67.0초.

이 문장 자체의 산수는 맞다. 틀린 것은 **거기 붙은 측정 조건**이다.

**67.0초/건은 축소 DB 측정값이 아니다.** 원자료 `results_example/msa_throughput.csv`
의 `db` 열이 조건을 명시하고 있다.

```
전체 DB 4종 각 4GB 슬라이스 (uniref90/mgnify/bfd/uniprot)
```

그런데 두 곳이 이것을 **축소 DB 라고 거꾸로** 적었다.

| 위치 | 정정 전 표기 | 문제 |
|---|---|---|
| `README.md` 1031행 | MSA **(축소 DB 기준)** 67.0초 / 37.2시간 / 93% | 조건이 반대다 |
| `docs/operations_guide.md` 699행 | MSA **(축소 DB, 코어 24 기준)** 67.0초 | 조건이 반대다 |

조건이 반대로 붙은 결과 **"연구자가 지금 쓰는 축소 DB 구성에서 MSA 가 전체의 93%"**
라는 잘못된 결론이 저장소 전체로 퍼졌다. 실제로는 그 반대다.

---

## 2. 원자료에 있는 서로 다른 네 개의 측정

이 값들은 **측정 조건이 달라 직접 비교할 수 없다.** 표에 조건을 붙이지 않으면
어느 것이든 오해를 만든다.

| 값 (건당) | 무엇을 쟀나 | DB 조건 | 근거 | 출처 |
|---|---|---|---|---|
| **1.98초** | AF3 데이터 파이프라인 전체 (`--norun_inference`) | 축소 DB 약 2GB | 직접측정, VHH 4건 | `docs/two_stage_notes.md` 3절 (D1) |
| **30.41초** | 같은 것, 같은 4건 대조 | 전체 DB 급 4종 각 4GB 슬라이스 | 직접측정, VHH 4건 | 같음 (D2) |
| **67.0초** | MSA 단계 스레드 스윕의 최대 처리율 (0.895 타깃/분) | 전체 DB 급 4종 각 4GB 슬라이스 | 인용, 14조합 스윕 | `results_example/msa_throughput.csv` |
| **13.14초** (범위 10.31~25.11) | jackhmmer **단독**, uniref90 **하나만**. 파이프라인 전체가 아니다 | 축소 세트 | 직접측정, 6건 평균 | `results_example/msa_comparison.csv` |
| **43.33초** | 파이프라인 + 추론 **end-to-end 전부** | 축소 DB | 직접측정, 6건 평균 (260초 / 6건) | `results_example/projection_2000.csv`, `docs/db_notes.md` |

읽는 법에 주의할 점 다섯.

1. **1.98초와 67.0초를 같은 축에 올려 비교하면 안 된다.** 전자는 축소 DB 2GB,
   후자는 4GB 슬라이스 4종이다. 같은 4건으로 두 DB 를 대조한 값은 1.98초 대 30.41초다.
2. **30.41초와 67.0초는 둘 다 '전체 DB 급 4GB 슬라이스 4종' 을 달고 있으면서 2배 넘게
   차이난다. 이 불일치는 아직 해소되지 않았고, 숨기지 않고 적어 둔다.**
   30.41초는 2단계 트랙이 VHH 4건으로 잰 데이터 파이프라인 직접측정이다
   (첫 건 91.70초 포함 평균이고, 2~4번째는 9.09~9.60초라 정상상태는 9~10초에 가깝다).
   67.0초는 DB 트랙이 14조합 스레드 스윕에서 찾은 포화점 인용값이다
   (24코어 호스트, `jackhmmer_n_cpu=12`, 동시 1갈래).
   즉 측정 트랙·호스트 상태·스레드 구성·측정 대상이 모두 다르다.
   **어느 쪽이 맞는지 이 정정으로는 판정할 수 없다.** 같은 호스트에서 같은 스레드
   구성으로 두 값을 다시 재지 않았기 때문이다(새 AF3 실행은 이 트랙의 범위가 아니다).
   그래서 저장소는 두 값을 **서로 다른 행으로 따로** 적고, 각 행에 측정 트랙과 근거를
   붙였다. 한 행으로 합치거나 둘 중 하나를 버리지 않았다.
3. **전체 DB 급 40.2시간은 두 값 중 느린 쪽(67.0초)을 쓴 값이다.** 같은 DB 급을
   30.41초로 잡으면 2000건 파이프라인이 16.9시간이 되어 합계는 약 19.9시간, MSA 비중은
   85%가 된다. 40.2시간은 그중 보수적인(긴) 쪽이다. 어느 쪽을 인용하든 **축소 DB 약 2GB
   구성(4.1시간, 비중 27%)과는 결론이 다르다**는 이 정정의 요지는 바뀌지 않는다.
4. **jackhmmer 단독 값을 MSA 단계 시간으로 쓰면 안 된다.** `msa_comparison.csv` 의
   축소 세트 10.31~25.11초는 **uniref90 하나만** 검색한 시간이다. AF3 데이터 파이프라인은
   DB 4종을 검색하고 특징화까지 하므로 같은 것이 아니다.
5. **43.3초는 MSA 시간이 아니다.** 이 값은 `projection_2000.csv` 와 `docs/db_notes.md`
   의 **축소 DB end-to-end 6건 평균**(260초 / 6건)으로, MSA 와 추론을 전부 포함한다.
   MSA 단계만의 시간과 섞지 말 것. (`msa_comparison.csv` 에는 43.3 이라는 값이
   존재하지 않는다. 이 문서를 쓰며 원자료를 다시 검색해 확인했다.)

## 3. 정정의 결론

### 축소 DB 구성에서 MSA 는 병목이 아니다

연구자가 실제로 쓰는 축소 DB 약 2GB 구성에서 데이터 파이프라인은 건당 1.98초로,
GPU 추론 5.39초보다 **짧다.**

| 구성 | 데이터 파이프라인 | GPU 추론 | 2000건 합계 | MSA 비중 |
|---|---|---|---|---|
| 축소 DB 약 2GB (권장) | 1.98초 = 1.1시간 | 5.39초 = 3.0시간 | **약 4.1시간** | 27% |
| 전체 DB 급 4GB 슬라이스 4종 | 67.0초 = 37.2시간 | 5.39초 = 3.0시간 | **약 40.2시간** | 93% |

각 단계 값은 직접측정(파이프라인·추론) 또는 인용(스윕 67.0초)이고,
**2000건 합계와 비중은 두 단계를 더한 합산 추정이다.** 두 단계를 겹치지 않고
순차 실행한다고 가정한 값이라 상한이다.

따라서 **"코드를 고치면 MSA 가 93%"** 라는 문장은 조건을 붙여야 성립한다.
전체 DB 급 구성에서만 참이다. 조건 없이 단정한 곳은 모두 고쳤다.

### `0.895 타깃/분` 은 지우지 않았다

유효한 측정값이다. 지우지 말고 **조건을 붙였다**: 전체 DB 급 구성에서의 포화점.
스레드를 96(코어 수의 4배)까지 늘려도 이 값을 못 넘는다는 결론도 그대로 유효하다.

### `_data.json` 재사용의 값도 다시 서술했다

정정 전에는 "MSA 가 93%이므로 재사용이 가장 큰 절약" 이라고 적혀 있었다.
축소 DB 구성에서는 그렇지 않다.

| 1단계 DB | 재사용의 시간 절약 (건당) | 근거 |
|---|---|---|
| 축소 DB 약 2GB | **1.7~5.3초** (작다) | 직접측정. 4건 A/B 전체 17.93 - 추론만 12.61~13.85 = 4.1~5.3초, 6건 정합 13.00 - 11.30 = 1.7초 |
| 전체 DB 급 4GB 슬라이스 4종 | **약 30초** | 직접측정. 데이터 파이프라인 30.41초를 건너뛴다 |

**축소 DB 에서 재사용을 권하는 진짜 이유는 시간이 아니다.** 1단계와 2단계가
완전히 같은 MSA 를 쓰게 된다는 것이 이득이다. 같은 축소 DB 로 MSA 를 새로 만들면
unpaired 깊이가 **9→7, 13→10, 12→9** 로 달라지는 것이 6건에서 실측됐다.
재사용은 원본 실행의 깊이를 6건 전건 그대로 보존했고, 두 번 돌려
ranking_score 와 pLDDT 평균이 소수점까지 같았다.

### 건드리지 않은 것

- `docs/install_log.md` 320행의 93% 는 **VRAM 점유율**이다. MSA 와 무관하다.
- `docs/two_stage_notes.md` 는 이미 정확하다. 정본이므로 손대지 않았다.
- `results_example/*.csv` 원자료는 수정하지 않았다. 조건이 이미 `db` 열에 적혀 있다.
- `tests/`, `docs/testing_notes.md` 의 "40시간 배치" 는 동시 실행 사고를 설명하는
  맥락이고 MSA 비중 주장이 아니다.
- 그림 패널 (a)(b)(c) 의 수치와 문구는 정확하므로 그대로 유지했다.

## 5. 다시 같은 실수를 막으려면

1. **MSA 시간을 인용할 때 DB 구성을 반드시 함께 적는다.** 축소 DB 약 2GB 인지
   4GB 슬라이스 4종인지를 빼면 값이 15배 차이난다.
2. **원자료의 조건 열을 먼저 읽는다.** `msa_throughput.csv` 는 `db` 열에,
   `projection_2000.csv` 는 `assumption` 열에 조건이 적혀 있다.
3. **직접측정과 합산 추정을 표에서 구분한다.** 2000건 합계는 어느 것도 실측이 아니다.
   건당 값만 실측이고 곱셈과 덧셈은 추정이다.
4. **"MSA 가 병목이다" 를 조건 없이 쓰지 않는다.** 축소 DB 에서는 GPU 추론이 더 길다.
