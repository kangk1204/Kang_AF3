# AF3 A/B 벤치마크 실측 리포트 (Phase 1)

측정 호스트: `ssh:gpu-5070ti` (RTX 5070 Ti 16GB, Blackwell sm_120, 24 CPU, RAM 126GB)
측정일: 2026-08-19 (한국시간 00:41–06:13)
AF3 commit `97d20234` (v3.0.4-15-g97d2023), jax 0.10.2, conda 네이티브 설치

## 0. 결론 한 줄

**연구자 스크립트를 단일 프로세스로 바꾸면 GPU 단계는 병목에서 사실상 사라진다
(건당 31.95초 → 5.39초, 5.93배). 그 다음에 무엇이 남는지는 1단계에 쓰는 DB 구성이
정한다.** 전체 DB 급(4종 각 4GB 슬라이스) 구성이라면 MSA(CPU) 가 병목이 되고
약 0.895 타깃/분에서 포화한다. 축소 DB 약 2GB 구성이라면 데이터 파이프라인이
건당 1.98초여서 MSA 가 병목이 아니다.

따라서 연구자에게 줄 메시지는 "코드만 고치면 수십 배"가 **아니다**. 정확히는:

> 코드를 고치면 GPU 단계는 2000건에 3시간으로 줄어든다. 그 다음은 DB 구성에 달렸다.
> 축소 DB 약 2GB 로 스크리닝하면 데이터 파이프라인이 1.1시간이라 총 약 4.1시간이고,
> 이때 MSA 는 병목이 아니다. 전체 DB 급으로 돌리면 MSA 37.2시간이 남고
> 이것은 프로세스를 몇 개로 쪼개도 줄지 않는다. 그 경우 다음 수단은 코드가 아니라
> **MSA 자체를 줄이는 것**(DB 축소, MSA 재사용, 사전 계산)이다.

2000건 환산: 현재 방식 189시간(7.9일) → 코드 최적화 후 축소 DB 구성 **약 4.1시간**,
전체 DB 급 구성 **약 40.2시간(1.7일, 이 중 MSA가 93%)**.

### 측정 완료

|---|---|---|

### 측정하지 못함 (추정으로 채우지 않았다)

1. **MSA 처리율을 이 트랙이 직접 재측정하지 못했다.** 리포트의 0.895 타깃/분은
   **다른 트랙(DB 트랙)이 14개 조합으로 실측한 값을 인용**한 것이고,
   그 측정 조건은 **전체 DB 급(4종 각 4GB 슬라이스)** 이다. 이 트랙의
   MSA 측정 작업은 호스트 작업 제출이 승인 대기에 걸려 실행되지 못했다.
   포화의 **원인**(디스크 I/O인지 CPU인지)도 따라서 직접 규명하지 못했다.
   단, 다른 트랙 스윕의 구조에서 CPU 쪽 근거는 읽을 수 있다 — 4절 참고.
   축소 DB 약 2GB 구성의 데이터 파이프라인 건당 1.98초는 2단계 트랙이 별도로 실측했다.
2. **MSA/추론 파이프라인 중첩 시의 실질 처리율**을 측정하지 못했다.
   GPU가 굶는지 여부는 미확인이다.
3. **샘플링 트레이드오프(경량 vs 기본값)의 순위 보존**을 측정하지 못했다.
   Spearman 상관, 상위 N 회수율, 권장 컷오프는 **수치 근거가 없다.** 이 트랙에서
   경량 설정의 신뢰도 지표를 한 건도 생산하지 못했으므로, 컷오프를 제안하지 않는다.
4. **16GB 토큰 상한**을 측정하지 못했다. unified memory 계열 설정의 실제 동작
   여부도 미확인이다. `token_ceiling.csv` 는 생성되지 않았다.
5. **콜드 상태 재현 불가.** sudo 없이 `drop_caches` 를 할 수 없다.
   **이 리포트의 모든 값은 페이지 캐시가 따뜻한 상태 기준**이다.
6. **Docker 대 네이티브 차이를 정량화하지 못했다.** 이 호스트에 Docker가 없다.

## 2. 2×2 A/B — 두 요인의 분리 (핵심 결과)

32건, 3회 반복, 중앙값. 조건 순서를 반복마다 회전시켜 interleaved 로 실행했다.
MSA 없음(`--norun_data_pipeline`), sample 5 × recycle 10.

| 방식 | 캐시 | 건당 wall | 3회 값 | 추론/건 | featurise/건 | 기타(기동)/건 |
|---|---|---|---|---|---|---|
| 프로세스별 | 미지정 | **31.95 s** | 31.84 / 31.95 / 31.98 | 21.71 | 1.05 | 9.19 |
| 프로세스별 | 지정 | **18.13 s** | 18.13 / 18.13 / 18.13 | 7.96 | 1.05 | 9.12 |
| 단일 프로세스 | 미지정 | **6.26 s** | 6.25 / 6.26 / 6.28 | 5.26 | 0.56 | 0.44 |
| 단일 프로세스 | 지정 | **5.39 s** | 5.39 / 5.39 / 5.41 | 4.40 | 0.55 | 0.44 |

반복 간 편차가 0.1% 수준이다. load1 은 전 구간 1.1–2.9 로 통제됐다.

### 효과 분해

| 개입 | 개선 배수 |
|---|---|
| 단일 프로세스화 (캐시 미지정 상태에서) | **5.10배** |
| 단일 프로세스화 (캐시 지정 상태에서) | **3.36배** |
| 캐시 디렉터리 지정만 (프로세스별 유지) | **1.76배** |
| 캐시 디렉터리 지정만 (단일 프로세스에서) | 1.16배 |
| 최악 → 최선 (프로세스별·무캐시 → 단일·캐시) | **5.93배** |

**해석 (연구자 처방에 직결):**

- **주효과는 단일 프로세스화다.** 캐시 디렉터리 지정만으로는 1.76배밖에 얻지 못한다
  (전체 5.93배 중 30% 수준). 사전 진단이 우려했던 "캐시만으로 대부분을 얻는다면
  그게 훨씬 쉬운 처방"이라는 시나리오는 **성립하지 않았다.**
- 다만 1.76배는 공짜다. `--jax_compilation_cache_dir` 한 줄이므로
  **작업을 쪼개야 하는 상황에서는 반드시 넣을 값**이다.
- 프로세스 기동 비용은 **건당 9.1–9.2초**로 계측됐다(캐시 여부와 무관 → 캐시가
  줄여주는 것은 컴파일이지 기동이 아니다). 단일 프로세스에서는 0.44초/건으로
  32건에 걸쳐 상환된다.
- **캐시는 프로세스 간에 실제로 적중한다** — 인계된 관측(3.63배)이 재확인됐다.
  단 이 트랙의 통제된 조건에서 배수는 1.76배로, 인계값보다 작다.
  인계 측정은 1건 반복이었고 이 측정은 32건이라, 건수가 많아질수록 캐시가 아닌
  기동 비용의 비중이 커져 배수가 줄어드는 것으로 보인다.

## 3. 상환 곡선과 길이순 정렬 — 인계 가정이 뒤집혔다

### 3.1 상환은 첫 2건에서 끝난다

96건 단일 프로세스, 길이순 정렬:

| 조건 | 1번째 | 2번째 | 3번째~ | 91번째 (버킷 전환) | 92번째~ |
|---|---|---|---|---|---|
| 캐시 지정 | 7.95 s | 6.87 s | **4.20 s** | 27.58 s | 9.44 s |
| 캐시 미지정 | 21.90 s | 20.62 s | **4.20 s** | 27.47 s | 9.43 s |

정상 상태는 두 조건 모두 **4.20초**로 동일하다. 캐시가 바꾸는 것은 **첫 2건의 비용**뿐이다
(21.9+20.6 = 42.5초 → 7.9+6.9 = 14.8초, 약 28초 절약). 96건에 28초는 건당 0.3초이므로
**규모가 커지면 캐시 지정의 이득은 0으로 수렴한다.** 이것이 2절에서 캐시 배수가
인계값보다 작게 나온 이유다.

버킷 128 → 256 전환(91번째)에서 27.6초로 재상승하고, 이후 9.44초로 안정된다.
버킷 256의 정상 상태(9.44초)는 버킷 128(4.20초)의 2.25배다 — 패딩 크기의 대가다.

### 3.2 길이순 정렬은 이 조건에서 이득이 없다 (예상과 다른 결과)

버킷 128 6건 + 버킷 256 6건 = 12건으로, 전환 횟수만 바꿔 비교했다.

| 순서 | 버킷 전환 | 캐시 지정 건당 | 캐시 미지정 건당 |
|---|---|---|---|
| 정렬 (128×6 → 256×6) | 1회 | 9.11 s | 12.58 s |
| 미정렬 (128,256 교대) | 11회 | 9.11 s | 12.65 s |
| **정렬 이득** | | **0.00 s/건 (1.000배)** | **0.07 s/건 (1.006배)** |

미정렬 조건의 순번별 추론 시간이 이유를 그대로 보여준다
(캐시 미지정, 버킷 128↔256 교대):

```
 1번째 버킷128 : 21.89s  <- 버킷128 컴파일
 2번째 버킷256 : 27.17s  <- 버킷256 컴파일
 3번째 버킷128 : 20.50s  <- 버킷128 컴파일 잔여
 4번째 버킷256 :  9.44s
 5번째 버킷128 :  4.20s
 6번째 버킷256 :  9.44s     ... 이후 전환해도 정상 상태 유지
```

**XLA는 버킷별 컴파일 결과를 프로세스 수명 동안 보유한다.** 각 버킷의 첫 등장에서만
컴파일하고, 그 뒤로는 버킷을 몇 번 왕복해도 재컴파일하지 않는다.

**따라서 인계 문서의 "정렬 미적용은 버킷이 오가며 재컴파일이 반복되어야 한다"는
가정은 이 스택에서 성립하지 않는다.** 인계 문서가 근거로 삼은 6건 시퀀스
(26.12 → 21.64 → 4.22 → 4.21 → 28.53 → 9.44)는 정렬된 순서였기 때문에
"버킷 전환 = 재컴파일"로 읽혔지만, 실제로는 "각 버킷의 첫 등장 = 컴파일"이었다.
두 해석은 정렬된 데이터에서 구별되지 않는다.

### 3.3 이 세트에서는 정렬 자체의 여지도 작다

벤치마크 96건(111–136 aa)의 버킷 분포는 **128에 90건, 256에 6건**이다.
연구자의 2000건도 VHH 단량체라면 비슷할 것이므로, 정렬 여부로 바뀔 수 있는 비용의
총량 자체가 작다.

**연구자 처방**: 길이순 정렬은 넣어도 손해가 없고 코드도 간단하지만,
**VHH 단량체 스크리닝에서 정렬로 얻는 시간은 실측 0에 가깝다.**
`--buckets=128,256` 로 불필요한 버킷을 잘라내는 것도 마찬가지로 이득이 미미하다.
정렬을 우선순위 높은 처방으로 제시하면 과장이 된다.

## 4. MSA 단계 — 여기가 진짜 병목 (인용 데이터)

**출처 주의: 이 절은 다른 트랙(DB 트랙)의 실측을 인용한 것이고, 이 트랙이 재측정한
값이 아니다.** 14개 조합 스윕, 전체 DB 4종 각 4GB 슬라이스.

| 총 스레드 | 최고 처리율 (타깃/분) |
|---|---|
| 4 | 0.195 |
| 8 | 0.374 |
| 16 | 0.673 |
| 24 | 0.778 |
| 32 | **0.890** |
| 48 | **0.895** |
| 96 | 0.848 (감소) |

측정 조건은 **전체 DB 급(4종 각 4GB 슬라이스)** 이다
(`results_example/msa_throughput.csv` 의 `db` 열). 축소 DB 약 2GB 에서는 데이터
파이프라인이 건당 1.98초다.

**호스트 코어 수(24)의 약 1.3배인 32스레드에서 포화하고, 그 이상은 늘지 않는다.
96스레드에서는 오히려 떨어진다.**

포화 지점이 코어 수 근방이고 과다 구독에서 성능이 하락하는 형태는 **CPU 포화의
전형적 패턴**이다. 다만 이 트랙이 디스크 읽기량을 직접 계측하지 못했으므로
**디스크 I/O 기여를 배제할 수는 없다** (축소 DB 2.0 GB는 RAM 126 GB에 충분히
들어가므로 반복 실행에서는 디스크가 병목이 아닐 것으로 예상되나, 미측정이다).

같은 조합 안에서 **동시 실행 갈래를 늘리는 것은 스레드 총량이 같으면 이득이 없다**:
`n_cpu=8 × 1갈래`(32스레드) = 0.890 vs `n_cpu=4 × 2갈래`(32스레드) = 0.767.
오히려 갈래를 늘린 쪽이 나쁘다. **AF3는 이미 체인당 4개 DB를
`ThreadPoolExecutor(max_workers=4)`로 병렬 검색하므로, 병렬성이 이미 내부에 있다.**

**연구자 처방**: MSA 단계는 `--jackhmmer_n_cpu 8~12` 로 **단일 갈래** 실행이 최선이다.
갈래를 6개로 쪼개는 것(af3_batch.py 기본값 `--msa-workers 4`)은 근거가 없고,
스레드 총량이 같으면 오히려 느리다.

### 축소 DB의 효과 (다른 트랙 인용)

| DB | jackhmmer(uniref90) 중앙값 | MSA 깊이 중앙값 |
|---|---|---|
| 축소 (2GB 슬라이스) | 10.5 s | 727 |
| 전체 (72GB) | 698.6 s | 23,916 |

**시간 66배, 깊이 33배 차이.** 연구자가 축소 DB를 쓰고 있는 것은 속도 면에서는
큰 이득이다(구조 품질 영향은 이 트랙 범위 밖).

## 5. VRAM — 인계값보다 더 낮게 나왔다

| 조건 | 최대 VRAM |
|---|---|
| 선점 ON (공식 Dockerfile 기본) | 15,157 MiB (인계값) |
| **선점 OFF, 이 트랙 18런 전체** | **2,942–2,963 MiB** |
| 선점 OFF (인계 측정) | 5,291 MiB |

**이 트랙의 모든 런에서 피크가 2,942–2,963 MiB 였다.** 인계값 5,291 MiB의 약 56%다.
차이의 원인은 규명하지 못했다(인계 측정은 호스트 고부하 중이었고 버킷 구성이 달랐다).
보수적으로 **VHH 단량체 추론의 실제 VRAM 요구량은 3–5.3 GB 범위**로 보는 것이 맞다.

어느 값을 쓰든 결론은 같다: **연구자의 "GPU 메모리가 꽉 차서 하나밖에 못 돌린다"는
전제는 틀렸다.** 32GB 카드에서 물리적으로는 여러 개가 들어간다.
단 2절이 보여주듯 **여러 프로세스를 띄우는 것은 잘못된 방향**이다 —
프로세스마다 9.1초의 기동 비용을 다시 내기 때문이다. 단일 프로세스가 답이다.

## 6. 2000건 환산

| 시나리오 | 건당 | 2000건 | 출처 |
|---|---|---|---|
| 연구자 현재 (5090, Docker, 타깃당 재기동) | 341 s | **189 h (7.9일)** | 연구자 보고 |
| [GPU만] 현재 방식 재현 (네이티브) | 31.95 s | 17.8 h | 이 트랙 실측 |

| [데이터 파이프라인만] 전체 DB 급 4GB 슬라이스 4종 | 30.41 s | 16.9 h | 다른 트랙 인용 (같은 4건) |

| **[전체] 전체 DB 급 구성 = MSA + GPU** | 72.4 s | **40.2 h (1.7일)** | 합산 추정 |
| [전체] 축소DB 6건 end-to-end 실측 | 43.3 s | 24.1 h | 다른 트랙 인용 |

### 개선 배수는 어느 것을 비교하느냐에 따라 다르다 — 정직하게 쓰면

- **GPU 단계만 비교하면 5.93배** (31.95 → 5.39초). 이것이 이 트랙이 직접 측정한 값이다.
- **연구자 현재값 대비 전체 파이프라인은 DB 구성에 따라 4.7~46배** (189h → 4~40h).
  하단(40.2h)은 전체 DB 급 MSA 37.2h 를 더한 합산 추정, 중간(24.1h)은 축소 DB
  end-to-end 6건 실측, 상단(4.1h)은 축소 DB 데이터 파이프라인 1.98초 + 추론 5.39초
  합산 추정이다. **DB 구성을 밝히지 않은 배수는 쓰지 말 것.**
- **"63배"처럼 341초와 5.39초를 직접 나눈 값은 쓰지 말아야 한다.**
  341초에는 MSA가 포함되고 5.39초에는 포함되지 않으므로 같은 것을 비교하지 않는다.

### 환산 가정 (모두 개선 배수를 과장하는 쪽이 아니라 축소하는 쪽으로 적었다)

1. **웜 상태 기준.** sudo 없어 콜드 재현 불가. 첫 실행은 이보다 느리다.
2. **네이티브 대 Docker.** 우리 값에는 컨테이너 기동 비용이 없다 →
   **현재 방식 재현값(31.95초)은 연구자 실제값의 하한**이다. 즉 실제 개선 배수는
   이 계산보다 클 수 있다.
3. **5070 Ti(16GB) 대 5090(32GB).** 5090이 더 빠르므로 절대 시간은 연구자 쪽이
   짧아질 것이다(추정). 개선 **배수**는 양쪽에 같은 방향으로 작용해 비교적 안정적일 것이다.
4. **MSA 37h 는 인용값이며 이 트랙이 재측정하지 않았다.** 또한 다른 트랙의 스윕은
   4GB 슬라이스 기준이므로, 연구자의 2GB 축소 DB에서는 더 빠를 수 있다
   (축소DB end-to-end 24.1h 가 그 방향을 시사한다).
5. **MSA/GPU 중첩 미측정.** 전체 DB 급 구성에서 두 단계를 겹치면 40.2h 보다 줄어들
   여지가 있으나(이론적 하한은 max(37.2, 3.0) = 37.2h), 실측하지 않았다.

## 7. 연구자에게 줄 처방 (우선순위 순, 근거 배수 포함)

1. **단일 프로세스 `--input_dir` 순회로 전환** — 실측 5.10배(캐시 없을 때).
   가장 큰 단일 개입이며 다른 모든 것보다 먼저 해야 한다.
2. **`--jax_compilation_cache_dir` 를 고정 경로로 지정** — 프로세스를 쪼개야 하는
   상황에서 1.76배. 단일 프로세스로 이미 바꿨다면 이득은 1.16배로 작고,
   2000건 규모에서는 사실상 0에 수렴한다(3.1절). 그래도 한 줄이니 넣어라.
3. **MSA 는 `--jackhmmer_n_cpu 8~12`, 갈래는 1개** — 갈래를 늘리는 것은 이득이 없고
   같은 스레드 총량에서 오히려 느리다(4절). `af3_batch.py --msa-workers` 기본값 4는
   근거가 없으므로 1로 두는 편이 낫다.
4. **VRAM 선점 끄기(`XLA_PYTHON_CLIENT_PREALLOCATE=false`)** — 실측 요구량 약 3 GB.
   메모리를 아끼려는 목적이 아니라, GPU를 다른 작업과 공유할 수 있게 하려는 목적이다.
   **여러 AF3 프로세스를 띄우기 위한 근거로 쓰지 말 것** — 그것은 1번과 반대 방향이다.
5. **길이순 정렬은 우선순위 낮음** — 실측 이득 0.00초/건(3.2절). 넣어도 손해는 없다.
6. **그 다음 개선은 코드가 아니라 MSA 자체를 줄이는 것 — 단, 전체 DB 급 구성일 때만
   크다** — 전체 DB 급(4GB 슬라이스 4종) 구성이라면 2000건 40.2시간 중 37.2시간이
   MSA다. 축소 DB 약 2GB 구성이라면 데이터 파이프라인이 건당 1.98초뿐이어서 여기서
   얻을 시간이 별로 없다 (그래도 MSA 재사용은 1단계와 2단계를 같은 MSA 로 묶는
   목적으로 권한다). DB를 더 줄이거나, 유사 서열의 MSA를 재사용하거나, MSA를 한 번
   만들어 보관해 두고 설정을 바꿔 재추론하는 전략이 남은 레버다.

## 8. 측정 설계상 통제한 것과 못 한 것

**통제한 것**
- load1 을 전 측정 구간 1.1–2.9 로 유지 (다른 트랙 작업이 끝날 때까지 대기 후 측정)
- A/B 조건을 반복마다 회전시켜 interleaved 실행 → 부하 드리프트가 한쪽에 실리지 않게
- 각 조건 3회 반복, 중앙값 사용 (반복 간 편차 0.1% 수준)
- 매 런의 load1·GPU 피크를 함께 기록 (`results_example/ab_benchmark.csv` 에 전량)
- 캐시 조건에서는 사전 예열 2건을 측정에서 제외 (정상 상태를 재려는 목적이므로)

**못 한 것**
- 콜드 상태(페이지 캐시 비운 상태) — sudo 없음
- Docker 경로 — 호스트에 Docker 없음
- MSA 단계 직접 측정 — 작업 제출이 승인 대기에 걸림
- 샘플링 트레이드오프·토큰 상한 — 같은 이유로 미실행

**측정 중 발견한 함정 (다음 트랙 참고)**
- 벤치마크 입력 tar.gz 가 macOS 에서 만들어져 압축 해제 시 AppleDouble 사이드카
  (`._*.json`) 96개가 함께 생긴다. `ls` 에는 안 보이지만 `glob("*.json")` 에 잡히고
  UTF-8 이 아니어서 읽으면 죽는다. 첫 3시간 측정이 이것 때문에 통째로 실패했다.
- `run_alphafold.py` 의 기본 버킷 사다리는 **128** 부터 시작한다.
  `af3_batch.py` 의 `DEFAULT_BUCKETS` 는 256 부터라 실제와 다르다. VHH 111–144 aa 가
  128 버킷에 들어가느냐 마느냐가 추론 시간을 2.25배 바꾸므로 이 차이는 중요하다.
