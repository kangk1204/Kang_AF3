## 0. 이 리포트가 세우는 구조

건당 시간의 대부분은 **1단계에 쓰는 DB 구성**이 정한다. 두 구성은 조건이 달라 직접
비교할 수 없다.

```
2000건, 축소 DB 약 2GB (연구자 현재 구성, 권장) = 약 4.1시간
├─ 데이터 파이프라인(MSA, CPU)  1.1시간  ███                     27%
└─ GPU 추론                     3.0시간  ████████                73%

2000건, 전체 DB 급 4GB 슬라이스 4종 = 약 40.2시간
├─ MSA (CPU)   37.2시간  ████████████████████████████████████████████ 93%
└─ GPU 추론     3.0시간  ███                                            7%
```

**측정의 결론은 "코드를 고치면 GPU 단계가 사라진다"이고, 그 다음에 무엇이 남는지는
DB 구성이 정한다.** 축소 DB 구성에서는 데이터 파이프라인 1.98초가 GPU 추론 5.39초보다
짧아 MSA 가 병목이 아니다. MSA 가 93%를 차지하는 것은 전체 DB 급 구성에서만 성립한다.
정정 경위는 `docs/msa_correction_notes.md`, 조건별 대조 측정은
`docs/two_stage_notes.md` 3절.

| | 건당 | 2000건 | 근거 |
|---|---|---|---|
| 연구자 현재 (5090, Docker, 타깃당 재기동) | 341초 | **189시간 (7.9일)** | 연구자 보고 |
| GPU 단계만: 현재 방식 재현 (네이티브) | 31.95초 | 17.8시간 | 직접측정 |
| GPU 단계만: 캐시 디렉터리만 추가 | 18.13초 | 10.1시간 | 직접측정 |
| GPU 단계만: **단일 프로세스 + 캐시 (권장)** | **5.39초** | **3.0시간** | 직접측정 |
| 데이터 파이프라인만: 축소 DB 약 2GB | **1.98초** | 1.1시간 | 인용 (2단계 트랙 실측, VHH 4건) |
| 데이터 파이프라인만: 전체 DB 급 4GB 슬라이스 4종 | 30.41초 | 16.9시간 | 인용 (같은 4건 대조) |
| MSA 단계만: 포화 처리율 0.895 타깃/분, 전체 DB 급 4GB 슬라이스 4종 | 67.0초 | **37.2시간** | 인용 (14조합 스윕) |
| **전체: 축소 DB 구성 (권장) = 파이프라인 + GPU** | **7.4초** | **4.1시간** | 합산 추정 |
| **전체: 전체 DB 급 구성 = MSA + GPU** | 72.4초 | **40.2시간 (1.7일)** | 합산 추정 |
| 전체: 축소DB 6건 end-to-end 실측 | 43.3초 | 24.1시간 | 인용 |

> **이 표의 '전체 DB 급' 은 4종 각 4GB 슬라이스(합계 16GB) 측정이다.** 공식 full DB 의
> MSA FASTA 4종은 실제로 305GB(bfd 17 + mgy 120 + uniprot 102 + uniref90 67)로 약 19배다.
> full DB 를 그대로 쓰면 이 표의 MSA 시간을 그만큼 넘어선다 — 단량체 1건 실측에서
> bfd 하나만 460초였고 25분 시점에도 나머지 3종이 돌고 있었다. **full DB 로 대량
> 스크리닝을 계획할 때 이 표의 40.2시간을 그대로 쓰면 안 된다.** 전수는 overlay 로,
> 상위 후보만 full DB 로 재계산하는 조합이 이 저장소의 권장이다.

## 1. 2×2 A/B — 두 요인을 분리했다

### 측정 설계

- 32건 × 3반복, 중앙값 사용. 조건 순서를 반복마다 회전시켜 **interleaved** 실행
  → 호스트 부하 드리프트가 한쪽 조건에 실리지 않게 했다.
- `--norun_data_pipeline` 으로 **MSA 없는 GPU 추론 경로만 격리**했다.
  (MSA 시간이 섞이면 요인 분리가 불가능하다)
- 매 런의 load1 과 GPU 피크를 함께 기록했다. 전 구간 load1 1.1–2.9 로 통제.
- 캐시 조건에서는 사전 예열 2건을 측정에서 제외했다 (정상 상태를 재려는 목적).

### 결과

| 방식 | 캐시 디렉터리 | 건당 wall | 3회 값 | 추론/건 | featurise/건 | 기동 등 기타/건 |
|---|---|---|---|---|---|---|
| 프로세스별 | 미지정 | **31.95초** | 31.84 / 31.95 / 31.98 | 21.71 | 1.05 | 9.19 |
| 프로세스별 | 지정 | **18.13초** | 18.13 / 18.13 / 18.13 | 7.96 | 1.05 | 9.12 |
| 단일 프로세스 | 미지정 | **6.26초** | 6.25 / 6.26 / 6.28 | 5.26 | 0.56 | 0.44 |
| 단일 프로세스 | 지정 | **5.39초** | 5.39 / 5.39 / 5.41 | 4.40 | 0.55 | 0.44 |

반복 간 편차가 0.1% 수준이다(예: 5.39 / 5.39 / 5.41). 이 정도 재현성이면
아래 배수들을 측정 오차로 설명할 수 없다.

### 효과 분해

| 개입 | 개선 배수 | 읽는 법 |
|---|---|---|
| **단일 프로세스화** (캐시 미지정 상태) | **5.10배** | 주효과. 가장 먼저 해야 하는 것 |
| 단일 프로세스화 (캐시 지정 상태) | 3.36배 | 캐시가 이미 일부를 가져갔으므로 배수가 줄어든다 |
| 캐시 디렉터리 지정만 (프로세스별) | 1.76배 | 부효과. 전체 5.93배 중 30% 수준 |
| 캐시 디렉터리 지정만 (단일 프로세스) | 1.16배 | 이미 단일 프로세스면 캐시의 여지가 작다 |
| **최악 → 최선** | **5.93배** | 31.95 → 5.39초 |

**핵심: 주효과는 단일 프로세스화다.** 사전 진단이 기대했던 "캐시 디렉터리 한 줄만
추가하면 대부분을 얻는다"는 쉬운 시나리오는 성립하지 않았다.

그리고 기동 비용을 직접 계측한 것이 이 표의 마지막 열이다.
**프로세스별 방식은 건당 9.1–9.2초를 기동에 쓰고, 그 값은 캐시 지정 여부와 무관하다.**
즉 캐시가 없애 주는 것은 컴파일이지 기동이 아니다.
단일 프로세스에서는 같은 비용이 32건에 상환되어 0.44초/건이 된다.

## 2. 상환 곡선 — 캐시의 이득은 배치 규모에 반비례한다

96건 단일 프로세스 순회, 길이순 정렬:

| 조건 | 1번째 | 2번째 | 3번째~ | 91번째 (버킷 전환) | 92번째~ |
|---|---|---|---|---|---|
| 캐시 지정 | 7.95초 | 6.87초 | **4.20초** | 27.58초 | 9.44초 |
| 캐시 미지정 | 21.90초 | 20.62초 | **4.20초** | 27.47초 | 9.43초 |

**정상 상태 4.20초는 두 조건에서 완전히 동일하다.**
캐시가 바꾸는 것은 첫 2건의 비용뿐이다: 21.9+20.6 = 42.5초가 7.9+6.9 = 14.8초로,
약 28초 절약. 96건에 28초면 건당 0.3초다.

**따라서 2000건 규모에서 `--jax_compilation_cache_dir` 의 이득은 0으로 수렴한다.**
그래도 붙여 두는 이유는 (a) 한 줄이고, (b) 중간에 멈췄다 다시 시작하는 상황에서는
프로세스가 새로 뜨므로 1.76배가 실제로 온다는 것이다.

이것이 1절에서 캐시 배수가 인계값(3.63배, 1건 반복 측정)보다 작게 나온 이유다.
건수가 많아질수록 캐시가 아닌 기동 비용의 비중이 커진다.

## 3. 패딩 버킷 — 128 인가 256 인가가 2.25배를 바꾼다

같은 96건 순회에서 91번째에 버킷이 128 → 256 으로 넘어갔고, 그 지점에서
27.6초로 재상승한 뒤 9.44초에 안정됐다.

| 버킷 | 정상 상태 추론 | 비고 |
|---|---|---|
| 128 | **4.20초** | VHH 111–128 aa 가 여기 들어간다 |
| 256 | **9.44초** | 129–256 aa. **2.25배 느리다** |

96건(111–136 aa)의 버킷 분포는 **128에 90건, 256에 6건**이었다.

**여기가 스크립트의 함정이었다.** `run_alphafold.py` 의 기본 버킷 사다리는
`128, 256, 384, 512, ...` 로 **128부터** 시작하는데, 초기 `af3_batch.py` 의
`DEFAULT_BUCKETS` 는 **256부터** 시작했다. 그러면 111 aa 서열도 256으로 패딩되어
전량이 2.25배 느린 경로를 탄다. 2000건 환산으로 GPU 단계 2.3시간이 5.2시간이 된다.
현재 버전에서 수정했다.

손으로 명령을 쓸 때도 마찬가지다. `--buckets=256` 만 주면 안 되고
`--buckets=128,256` 이어야 한다.

## 4. 길이순 정렬 — 인계 가정이 실측으로 뒤집혔다

버킷 128 6건 + 버킷 256 6건 = 12건으로, **전환 횟수만** 바꿔 비교했다.

| 순서 | 버킷 전환 횟수 | 캐시 지정 건당 | 캐시 미지정 건당 |
|---|---|---|---|
| 정렬 (128×6 → 256×6) | 1회 | 9.11초 | 12.58초 |
| 미정렬 (128, 256 교대) | 11회 | 9.11초 | 12.65초 |
| **정렬 이득** | | **0.00초/건 (1.000배)** | 0.07초/건 (1.006배) |

미정렬 조건의 순번별 추론 시간이 이유를 그대로 보여준다
(캐시 미지정, 버킷 128↔256 교대):

```
 1번째 버킷128 : 21.89초   <- 버킷128 컴파일
 2번째 버킷256 : 27.17초   <- 버킷256 컴파일
 3번째 버킷128 : 20.50초   <- 버킷128 컴파일 잔여
 4번째 버킷256 :  9.44초
 5번째 버킷128 :  4.20초
 6번째 버킷256 :  9.44초   ... 이후 몇 번을 전환해도 정상 상태 유지
```

**XLA는 버킷별 컴파일 결과를 프로세스 수명 동안 보유한다.**
컴파일은 각 버킷의 **첫 등장에서만** 일어난다.

인계 문서의 "정렬하지 않으면 버킷이 오가며 재컴파일이 반복된다"는 가정은
이 스택에서 **성립하지 않는다.** 인계 문서가 근거로 삼은 6건 시퀀스
(26.12 → 21.64 → 4.22 → 4.21 → 28.53 → 9.44)는 정렬된 순서였기 때문에
"버킷 전환 = 재컴파일"로 읽혔지만, 실제로는 "각 버킷의 첫 등장 = 컴파일"이었다.
**두 해석은 정렬된 데이터에서 구별되지 않는다.**

정렬은 스크립트에 남겨 두었다(로그를 읽기 쉽게 하고 버킷 목록을 좁히는 부수 효과가 있다).
그러나 **시간 절약 수단으로 제시하면 과장이다.**

## 5. VRAM — 선점을 끄면 3GB 급이다

| 조건 | 최대 VRAM | 출처 |
|---|---|---|
| 선점 ON (공식 Dockerfile 기본값) | 15,157 MiB | 인용 |
| **선점 OFF, 이 트랙 18런 전체** | **2,942–2,963 MiB** | 직접측정 |
| 선점 OFF (이전 측정, 호스트 고부하 중) | 5,291 MiB | 인용 |

18런 전체에서 피크가 2,942–2,963 MiB 로 매우 좁게 모였다.
이전 측정 5,291 MiB 의 약 56%이고, **차이 원인은 규명하지 못했다**
(이전 측정은 호스트 고부하 중이었고 버킷 구성이 달랐다).
보수적으로 **3–5.3 GB 범위**로 보는 것이 맞다.

어느 값을 쓰든 결론은 같다:

- `nvidia-smi` 가 15GB를 쓰는 것처럼 보이는 것은 **예약(선점)이지 수요가 아니다.**
- 실제 수요는 32GB 카드에서 10% 안쪽이다.
- **그러나 이것을 "여러 프로세스를 띄울 근거"로 쓰면 안 된다.**
  1절이 보여주듯 프로세스를 늘리면 기동 비용 9.1초를 그만큼 다시 낸다.
  선점을 끄는 목적은 GPU를 다른 작업과 **공유**할 수 있게 하는 것이다.

## 6. MSA 단계 — 여기가 진짜 병목 (인용 데이터)

**출처 주의: 이 절은 다른 트랙의 14조합 스윕 실측을 인용한 것이며, A/B 트랙이
재측정한 값이 아니다.** A/B 트랙의 MSA 측정 작업은 호스트 작업 제출이 승인 대기에
걸려 실행되지 못했다.

| 총 요구 스레드 | 최고 처리율 (타깃/분) | 건당 |
|---|---|---|
| 4 | 0.195 | 307초 |
| 8 | 0.374 | 160초 |
| 16 | 0.673 | 89초 |
| 24 | 0.778 | 77초 |
| 32 | **0.890** | 67.4초 |
| 48 | **0.895** | 67.0초 |
| 96 | 0.848 (감소) | 70.8초 |

**측정 조건: 전체 DB 급(4종 각 4GB 슬라이스)** 이다
(`results_example/msa_throughput.csv` 의 `db` 열). 축소 DB 약 2GB 는 데이터 파이프라인이
건당 1.98초여서 이 표의 포화점과 비교할 대상이 아니다.

**호스트 코어 수(24)의 약 1.3배인 32스레드에서 포화하고, 96스레드에서는 오히려 떨어진다.**

같은 스레드 총량에서 동시 실행 갈래를 늘리는 것은 손해다:

| 구성 | 총 스레드 | 처리율 |
|---|---|---|
| `n_cpu=8` × 1갈래 | 32 | **0.890** |
| `n_cpu=4` × 2갈래 | 32 | 0.767 |

이유는 AF3 소스에 있다. `pipeline.py:96` 에서 단백질 체인 1개당 DB 4개를
`ThreadPoolExecutor(max_workers=4)` 로 동시 검색한다. 즉 **1건당 실효 스레드 =
`n_cpu` × 4** 이고, **병렬성이 이미 코드 안에 있다.** 여기에 프로세스를 더 얹으면
컨텍스트 스위칭과 메모리 대역폭 경쟁만 늘어난다.

AF3 문서도 같은 이야기를 한다 (`docs/performance.md`): 최적 코어 수는
jackhmmer 프로세스 하나에 주는 코어 수의 4배라는 서술이다.

### 권장 설정

```
--jackhmmer_n_cpu = min(코어수 / 2, 8)
--nhmmer_n_cpu    = 같은 값
동시 실행 갈래     = 1
```

| 코어 수 | 권장 `n_cpu` | 동시 갈래 |
|---|---|---|
| 8 | 4 | 1 |
| 12 | 6 | 1 |
| 16 | 8 | 1 |
| 24 이상 | 8 (AF3 기본 상한) | 1 |

**AF3 기본값이 `min(cpu_count, 8)` 이므로 8코어 이상 머신에서는 기본값이 이미
최적에 가깝다.** 연구자가 손댈 필요가 없는 부분이고, 오히려 손대지 말아야 하는 부분이다.

포화 원인이 CPU인지 디스크 I/O인지는 **미측정**이다. 포화점이 코어 수 근방이고
과다구독에서 하락하는 형태는 CPU 포화의 전형적 패턴이지만, 디스크 읽기량을
직접 계측하지 않았으므로 단정할 수 없다.

## 7. 2000건 환산과 그 가정

### 환산

| 시나리오 | 건당 | 2000건 | 출처 |
|---|---|---|---|
| 연구자 현재 | 341초 | 189시간 (7.9일) | 연구자 보고 |
| GPU만: 현재 방식 재현 | 31.95초 | 17.8시간 | 직접측정 |
| GPU만: 캐시만 추가 | 18.13초 | 10.1시간 | 직접측정 |
| GPU만: 단일 프로세스 + 캐시 | 5.39초 | 3.0시간 | 직접측정 |
| 데이터 파이프라인만: 축소 DB 약 2GB | 1.98초 | 1.1시간 | 인용 (2단계 트랙 실측, VHH 4건) |
| 데이터 파이프라인만: 전체 DB 급 4GB 슬라이스 4종 | 30.41초 | 16.9시간 | 인용 (같은 4건) |
| MSA만: 포화 처리율 0.895 타깃/분, 전체 DB 급 4GB 슬라이스 4종 | 67.0초 | 37.2시간 | 인용 (14조합 스윕) |
| **전체: 축소 DB 구성 (권장)** | 7.4초 | **4.1시간** | 합산 추정 |
| **전체: 전체 DB 급 구성** | 72.4초 | **40.2시간 (1.7일)** | 합산 추정 |
| 전체: 축소DB 6건 end-to-end 실측 | 43.3초 | 24.1시간 | 인용 |

### 개선 배수를 정직하게 쓰면

- **GPU 단계만 비교하면 5.93배** (31.95 → 5.39초). 이것이 직접 측정한 값이다.
- **연구자 현재값 대비 전체 파이프라인은 DB 구성에 따라 4.7~46배** (189h → 4~40h).
  하단(40.2h)은 전체 DB 급 MSA 37.2h 를 더한 합산 추정, 중간(24.1h)은 축소 DB
  end-to-end 6건 실측, 상단(4.1h)은 축소 DB 데이터 파이프라인 1.98초 + 추론 5.39초
  합산 추정이다. **DB 구성을 밝히지 않은 배수는 쓰지 말 것.**
- **"63배"처럼 341초와 5.39초를 직접 나눈 값은 쓰면 안 된다.**
  341초에는 MSA와 컨테이너 기동이 포함되고 5.39초에는 둘 다 없으므로
  같은 것을 비교하지 않는다.

### 40.2시간은 전체 DB 급 구성의 상한이다

MSA와 GPU를 겹치지 않고 순차 실행한다는 가정의 합산이며, **MSA 67.0초/건은
전체 DB 급(4종 각 4GB 슬라이스) 측정값**이다.
두 단계는 서로 다른 자원(CPU 대 GPU)을 쓰므로 파이프라인으로 겹칠 여지가 있고,
**전체 DB 급 구성의 이론적 하한은 max(37.2, 3.0) = 37.2시간**이다.

주의: 이 40.2시간은 MSA 를 67.0초/건(스레드 스윕 포화점 인용)으로 잡은 값이다. 같은
전체 DB 급을 2단계 트랙의 직접측정 30.41초/건으로 잡으면 합계는 약 19.9시간, MSA 비중은
85%가 된다. 두 값이 같은 DB 급을 달고 2배 넘게 차이나는 것은 아직 해소되지 않았다
(측정 트랙·호스트·스레드 구성이 다르다). 근거와 경위는 `docs/msa_correction_notes.md` 2절.

### 환산 가정 (모두 개선 배수를 축소하는 쪽으로 적었다)

1. **웜 캐시 기준.** sudo 없이 `drop_caches` 를 할 수 없어 콜드 상태를 재현하지 못했다.
   첫 실행은 이보다 느리다.
2. **네이티브 대 Docker.** 측정 호스트에 Docker가 없어 conda 네이티브로 설치했다.
   즉 우리 값에는 컨테이너 기동 비용이 없다 → **현재 방식 재현값 31.95초는
   연구자 실제값의 하한**이다. 실제 개선 배수는 이 계산보다 클 수 있다.
3. **MSA 37h 는 인용값**이며 A/B 트랙이 재측정하지 않았다. 또한 그 스윕은 전체 DB의
   4GB 슬라이스 기준이므로, 연구자의 2GB 축소 DB에서는 더 빠를 수 있다
   (축소DB end-to-end 24.1시간이 그 방향을 시사한다).
4. **MSA/GPU 중첩 미측정.**

## 8. 5070 Ti(16GB) 대 5090(32GB) — 무엇이 달라지고 무엇이 안 달라지나

| 항목 | 이 측정 (5070 Ti 16GB) | 연구자 (5090 32GB) | 판단 |
|---|---|---|---|
| GPU 세대 | Blackwell sm_120 | Blackwell sm_120 | **동일 아키텍처** |
| VRAM | 16 GB | 32 GB | 둘 다 여유 (수요 3–5.3GB) |
| 절대 추론 시간 | 4.20초 (버킷 128) | 더 짧을 것 | **추정** — 5090이 연산 유닛·대역폭 모두 크다 |
| 개선 **배수** | 5.93배 | 비슷할 것 | **추정** — 기동/컴파일 비용은 양쪽에 같은 방향으로 작용 |
| 실행 방식 | conda 네이티브 | Docker | **우리 값에 컨테이너 기동 비용이 빠져 있다** |
| CPU | 24코어 | 미확인 | MSA 처리율은 코어 수에 직접 좌우된다 |

**주 결론으로 배수를 쓰고 절대 시간은 참고로만 쓰는 이유가 이것이다.**
5090에서는 절대 시간이 더 짧아지겠지만, 그것은 개선 배수를 바꾸지 않는다 —
기동 비용과 컴파일 비용은 하드웨어가 빨라지면 함께 줄어든다.

**연구자 쪽의 빠른 실행 경로 확인:**
```bash
bash af3run.sh vhh_001 bench     # 가장 짧은 20건, sample 1/recycle 3 스모크
```
이 값은 표의 sample 5/recycle 10 조건과 직접 비교할 수 없다. 처리시간을 계획하려면
버킷별 표본을 고르고 실제 운영과 같은 sample/recycle 설정으로 별도 pilot을 실행한다.
CPU 코어 수도 함께 확인해 두면 MSA 환산 조건을 기록할 수 있다:
```bash
nproc
```

### 16GB 카드의 토큰 상한은 측정하지 못했다

**미측정.** VHH 단량체(135 토큰)에서 VRAM 수요가 3GB 급이었다는 사실만 있고,
어느 토큰 수에서 16GB가 부족해지는지는 재지 않았다.
`token_ceiling.csv` 는 생성되지 않았다. unified memory 계열 설정
(`TF_FORCE_UNIFIED_MEMORY=true`)의 실제 동작 여부도 확인하지 않았다.
따라서 **항원-나노바디 복합체(토큰 수가 몇 배로 늘어난다)로 넘어갈 때의
메모리 여유는 이 측정으로 보증할 수 없다.** 32GB 카드이므로 상황은 우리보다 유리하지만,
첫 복합체 1건을 돌려 `nvidia-smi` 로 직접 확인하는 것이 맞다.

## 10. 측정 설계에서 통제한 것과 못 한 것

**통제한 것**
- load1 을 전 측정 구간 1.1–2.9 로 유지 (다른 트랙 작업 종료를 기다린 뒤 측정)
- A/B 조건을 반복마다 회전시켜 interleaved 실행
- 각 조건 3회 반복, 중앙값 사용 (반복 간 편차 0.1%)
- 매 런의 load1·GPU 피크 동시 기록 (`results_example/ab_benchmark.csv` 에 18런 전량)
- 캐시 조건에서 예열 2건을 측정에서 제외

**못 한 것**
- 콜드 상태 (sudo 없음)
- Docker 경로 (호스트에 Docker 없음)
- MSA 단계 직접 측정 (작업 제출이 승인 대기)
- 경량 설정의 순위 보존, 16GB 토큰 상한 (같은 이유로 미실행)
- MSA/GPU 중첩 처리율

**측정 중 잃은 3시간 — 다음 사람을 위한 기록**
벤치마크 입력 `tar.gz` 가 macOS 에서 만들어져, 리눅스에서 풀 때
AppleDouble 사이드카 `._*.json` 96개가 함께 생겼다.
`ls` 에는 보이지 않지만 `glob("*.json")` 에는 잡히고, UTF-8 이 아니어서
읽는 순간 `UnicodeDecodeError` 로 죽는다. **첫 3시간 측정이 이것 때문에 통째로 실패했다.**
`af3_batch.py` 와 `af3_collect.py` 는 이제 `._` 접두어 파일을 전부 건너뛴다.
남의 컴퓨터에서 받은 tar 를 풀 때는 항상 이것을 확인하라:
```bash
ls -a vhh_001_in | grep '^\._' | wc -l     # 0 이 아니면 사이드카가 있다
find vhh_001_in -name '._*' -delete        # 지워도 안전하다
```
