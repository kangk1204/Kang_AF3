# AlphaFold 3 배치 속도 진단 노트

작성 트랙: 진단 + 실행 세트 (원격 GPU 실측은 별도 트랙에서 병행)

## 표기 규칙

이 문서는 근거의 등급을 반드시 구분해서 적는다.

| 표기 | 뜻 |
|---|---|
| **[관측]** | 연구자가 실제로 겪은 값 (연휴 3일 72시간 / 760건 완료) |
| **[전달받은 전제]** | 이 작업 지시서가 "재조사 불필요한 확정 진단"으로 준 내용. 출처로 공식 저장소 이슈 번호(#468, #485, #488)가 함께 제시되었으나 **이 트랙이 해당 이슈 본문을 직접 읽어 확인한 것은 아니다.** 아래 "근거의 한계" 참고 |
| **[측정]** | 이 트랙이 로컬에서 스크립트를 실제로 실행해 얻은 출력 |
| **[추정]** | 이 트랙이 산술로 계산한 값. 실측 아님. 실측 트랙 결과로 대체되어야 함 |
| **[미확인]** | 확인하려 했으나 이 트랙에서 근거를 확보하지 못한 것. 추측으로 채우지 않았다 |

### 근거의 한계 (먼저 밝힘)

이 트랙은 웹 검색으로 공식 저장소 이슈 #468 / #485 / #488 과 `docs/performance.md` 의
**본문을 확보하지 못했다.** 검색 결과가 제목과 URL만 반환하고 본문 필드가 아예 없었다.

따라서 이 문서가 이슈 번호와 함께 서술하는 동작들은 **작업 지시서가 전제로 전달한
내용**이며, 이 트랙이 원문을 대조해 검증한 것이 아니다. `[문헌]` 대신
`[전달받은 전제]` 로 표기한 이유가 이것이다. 원문을 인용해야 하는 자리에서는
반드시 해당 이슈를 직접 열어 확인하고 인용할 것.

이 구분이 실무에 주는 영향은 제한적이다. 최적화의 방향(프로세스를 합친다)은
**전제가 틀려도 유효**하다 — 컨테이너 기동·JAX 초기화·가중치 로드를 N번에서 1번으로
줄이는 이득은 XLA 캐시의 세부 동작과 무관하게 존재한다. 전제에 의존하는 것은
"컴파일이 고정 오버헤드에서 얼마나 큰 몫인가"라는 **비중 추정**뿐이고,
그 값은 실측 트랙의 A/B가 확정한다(단일 프로세스에서 둘째 타깃부터 시간이
급락하면 전제와 부합, 아니면 전제를 수정해야 한다).

## 1. 관측값의 산술적 분해

**[관측]** 72시간 / 760건 = 건당 **341초 = 5.68분**.

원본 `run_af3_batch.py` 는 `for json_file in json_files:` 루프 안에서 JSON 하나마다
`sudo docker run --rm` 을 새로 띄운다. 따라서 건당 341초는 아래 6개 항목의 **합**이다.

```
건당 341초 = ① 컨테이너 기동/폐기
            + ② JAX·CUDA 초기화 (import, GPU 컨텍스트 생성)
            + ③ 가중치 로드 (~1GB 파일을 디스크→호스트RAM→VRAM)
            + ④ XLA 커널 컴파일          ← 여기가 핵심
            + ⑤ MSA 검색 (CPU, 축소 DB)
            + ⑥ 순수 확산 추론 (GPU)
```

①~④는 **타깃 내용과 무관한 고정 오버헤드**다. 즉 760번 반복해서 760배로 지불했다.
⑤~⑥만이 타깃마다 실제로 필요한 계산이다.

### 왜 ④가 핵심인가

**[전달받은 전제]** 지시서가 공식 저장소 이슈 #468 을 출처로 제시한 동작
(이 트랙은 원문을 확보하지 못했다):

- 같은 프로세스 안에서 `--input_dir` 로 여러 입력을 순회하면, 패딩 버킷 크기가 같을 때
  XLA **인메모리** 캐시에 적중해서 재컴파일을 건너뛴다.
- 반면 **프로세스가 다르면** 버킷 크기·모델·환경이 완전히 동일해도
  영구 컴파일 캐시(`--jax_compilation_cache_dir`)가 **적중하지 않는다.**
  캐시 폴더에 파일은 쌓이는데 재사용되지 않는다고 전해진다(위 전제의 일부).

원본 스크립트는 타깃마다 프로세스를 새로 띄우므로, **캐시가 구조적으로 무력화되는
최악의 패턴**에 정확히 해당한다. `--jax_compilation_cache_dir` 를 지금 추가해도
이 방식에서는 효과가 없다. 프로세스를 합치는 것이 선행 조건이다.

### ⑤가 작을 수밖에 없는 이유

**[관측]** 연구자는 공식 전체 DB(630GB급)가 아니라 축소 DB(~2GB)를 쓰고 있다.
MSA 검색 시간은 검색 대상 DB 크기에 지배되므로, 2GB DB에서의 jackhmmer 검색은
630GB DB 대비 훨씬 짧다. 즉 **건당 341초의 대부분이 MSA일 가능성은 낮다.**

### ⑥이 작을 수밖에 없는 이유

**[관측]** 타깃은 130 aa 내외 VHH/나노바디 단량체다.
`af3_batch.py` 의 토큰 계산기로 확인한 결과 **(측정: 스크립트 실행 출력 그대로)**:

```
 128 aa -> 토큰  128 -> 버킷 256
 131 aa -> 토큰  131 -> 버킷 256
 256 aa -> 토큰  256 -> 버킷 256
 257 aa -> 토큰  257 -> 버킷 512
 420 aa -> 토큰  420 -> 버킷 512
 610 aa -> 토큰  610 -> 버킷 768
 140aa x2체인 + ATP -> 토큰 310 -> 버킷 512
 VHH 2000건이 모두 120~135aa 라면 버킷: [256]
```

마지막 줄이 이 진단의 핵심이다. 즉 2000건이 모두 120~135 aa 라면
**전부 256 토큰 버킷 하나에 들어간다.**
AF3 추론 비용은 토큰 수에 대해 급격히 증가하므로, 256 버킷은 AF3가 다루는 범위에서
가장 작은 축이다. 대형 복합체(수천 토큰)에서 문제가 되는 추론 시간이
여기서는 지배 항목이 되기 어렵다.

### 산술적 결론 — 고정 오버헤드 비중

⑤+⑥(진짜 계산)이 얼마든, 나머지가 ①~④(고정 오버헤드)다.
가정 범위를 넓게 스캔한 결과 **[추정]**:

| 순수 추론 ⑥ | MSA ⑤ | 고정 오버헤드 ①~④ | 고정 비중 |
|---|---|---|---|
| 10초 | 10초 | 321초 | **94%** |
| 30초 | 20초 | 291초 | **85%** |
| 45초 | 30초 | 266초 | **78%** |
| 60초 | 30초 | 251초 | **74%** |

가정을 아무리 보수적으로 잡아도(순수 계산에 90초를 몰아줘도)
**고정 오버헤드가 건당 시간의 74% 이상**이다. 낙관적으로 보면 94%다.

이것이 이 진단의 핵심 숫자다. **연구자가 개선해야 하는 것은 GPU 성능도, 동시 실행
개수도 아니라, 760번 중복 지불한 고정 오버헤드다.**

**[미확인]** ①~④ 각각의 개별 소요 시간은 이 트랙에서 확정하지 못했다.
특히 "첫 XLA 컴파일이 몇 분급인가"는 웹 검색으로 본문을 확보하지 못해
구체적 수치를 인용하지 않았다. 이 분해는 실측 트랙의 A/B 벤치마크에서
`--input_dir` 순회 로그의 첫 타깃 대 둘째 타깃 시간 차이로 확정해야 한다.
(첫 타깃 = ①~④ 포함, 둘째 타깃부터 = ⑤+⑥만. 그 차이가 곧 고정 오버헤드다.)

## 2. 개선 후 예상치 (추정)

고정 오버헤드를 N배가 아니라 1회로 압축하면:

```
현재 방식                : 341초 × 2000건        = 약 189 시간 (약 7.9일)
최적화 후 (보수적 60초/건): 60×2000 + 900        = 약 33.6 시간  → 개선 5.6배
최적화 후 (중간   40초/건): 40×2000 + 900        = 약 22.5 시간  → 개선 8.4배
최적화 후 (낙관   25초/건): 25×2000 + 900        = 약 14.1 시간  → 개선 13.4배
```

**[추정]** 위 표의 "건당 초"는 가정값이다. 실측 트랙이 이 자리를 채워야 한다.
다만 **개선 배수가 5배 이상**이라는 결론은 가정 범위 전체에서 유지된다.
경량 스크리닝 설정(확산 샘플 1, 리사이클 3)을 함께 쓰면 ⑥이 더 줄어든다.

## 3. GPU 메모리가 꽉 차 보이는 현상 (연구자 질문 3번)

### 관측된 현상

연구자는 `nvidia-smi` 에서 VRAM이 거의 꽉 찬 것을 보고
"한 번에 하나밖에 못 돌린다"고 판단했다.

### 원인: 선점(preallocation)이지 실사용이 아니다

JAX는 기본적으로 프로세스 시작 시 GPU 메모리를 **미리 크게 확보**한다
(`XLA_PYTHON_CLIENT_PREALLOCATE`, `XLA_CLIENT_MEM_FRACTION`).
이는 실행 중 단편화를 막기 위한 설계로, **실제 사용량과 무관하게** 큰 덩어리를 잡는다.
(이것은 JAX의 일반적으로 알려진 기본 동작이다.)

연구자 이미지에 이 값들이 어떻게 설정되어 있는지는 **이 트랙이 확인하지 않았다.**
`af3_check.sh` 4번 항목이 `docker image inspect` 로 실제 값을 그대로 찍으므로,
그 출력을 근거로 삼을 것.

따라서 `nvidia-smi` 의 `memory.used` 는 **"AF3가 이만큼 필요하다"가 아니라
"AF3가 이만큼 예약했다"** 로 읽어야 한다. 130 aa 단량체(256 토큰 버킷)가
32GB를 실제로 다 쓸 이유는 없다.

**[미확인]** 이 이미지에 박혀 있는 정확한 환경변수 값은 연구자 PC에서 확인해야 한다.
`af3_check.sh` 4번 항목이 `docker image inspect` 로 실제 값을 그대로 찍는다.
추측으로 쓰지 말고 그 출력을 근거로 삼을 것.

### 실사용량을 드러내는 방법

```bash
docker run --rm --gpus all \
  -e XLA_PYTHON_CLIENT_PREALLOCATE=false \
  -e XLA_CLIENT_MEM_FRACTION=1.0 \
  ... (이하 동일)
```

동시에 다른 터미널에서:

```bash
nvidia-smi --query-gpu=timestamp,memory.used,utilization.gpu --format=csv -l 1 | tee vram_trace.csv
```

선점을 끈 상태의 **최대** `memory.used` 가 실제 필요량이다.
`af3_batch.py --no-prealloc` 이 이 설정을 자동으로 붙인다.

### 그럼에도 추론 프로세스를 다중화하면 안 되는 이유

VRAM이 남는다는 것이 확인되더라도, **단일 GPU에서 추론 프로세스를 2개 이상
띄우는 것은 권하지 않는다.** 이유는 세 가지다.

1. **직렬화** — GPU의 SM은 하나의 자원이다. 프로세스 2개가 커널을 제출하면
   시간분할로 번갈아 실행된다. 각 프로세스가 GPU를 100% 활용하고 있었다면
   합산 처리량은 늘지 않고, 각각이 2배 느려질 뿐이다.
2. **고정 오버헤드 중복** — 프로세스마다 CUDA 컨텍스트(수백 MB), 가중치 사본,
   그리고 #468 전제가 맞다면 **④ XLA 컴파일까지 다시** 지불한다. 우리가 줄이려는 바로 그 비용을
   프로세스 수만큼 다시 늘리는 셈이다.
3. **OOM 위험** — 선점을 끄면 메모리 확보가 동적이 되므로, 두 프로세스가 동시에
   피크에 도달하면 한쪽이 죽는다. 2000건 배치 도중에 죽는 것이 가장 나쁘다.

**결론: 추론 단계의 정답은 "프로세스 1개로 전수 순회"다.** 다중화가 아니라
오버헤드 제거가 이득의 원천이다.

### 진짜 병렬화 이득이 있는 곳: CPU MSA 단계

MSA 검색(jackhmmer/nhmmer)은 **CPU 작업이고 GPU를 전혀 쓰지 않는다.**
연구자 PC의 코어 수를 `af3_check.sh` 1번 항목에서 확인한 뒤,
이 단계만 여러 갈래로 동시 실행하면 실제로 벽시계 시간이 줄어든다.

수치 논리 **[추정]**:

```
코어 24개, MSA 갈래 6개 × 갈래당 검색 스레드 4개 = 24 스레드
MSA가 건당 20초라면:
  직렬  : 20초 × 2000건            = 11.1 시간
  6갈래 : 20초 × 2000건 / 6        =  1.9 시간   (약 6배 단축, 스케일링 손실 무시)
```

여기서 중요한 점: **MSA 단계에는 GPU를 붙이지 않는다**(`--gpus all` 없이 실행).
그래야 GPU가 유휴 상태로 낭비되지 않고, 나아가
**MSA(CPU)와 추론(GPU)을 시간적으로 겹칠 수 있다.**
`af3_batch.py --stage msa` 로 MSA를 먼저 쌓아두고 `--stage infer` 로 추론을 돌리면
GPU는 MSA를 기다리며 놀지 않는다.

## 4. 최적화 항목별 기대 효과 정리

| 항목 | 무엇을 없애는가 | 기대 효과 | 근거 등급 |
|---|---|---|---|
| 단일 프로세스 `--input_dir` | ①②③④ 를 N배 → 1배 | 가장 큰 항목. 건당 74~94% 차지분을 압축 | [전달받은 전제]+[추정] |
| 토큰 길이 정렬 + `--buckets` 축소 | 버킷 전환에 따른 재컴파일 | VHH 균일 배치면 버킷 1개 → 재컴파일 1회 | [전달받은 전제]+[측정] |
| MSA/추론 2단계 분리 | GPU 유휴 대기 | MSA를 코어 수만큼 병렬화 | [추정] |
| 경량 스크리닝 설정 | ⑥ 순수 추론량 | 확산 샘플 5→1, 리사이클 10→3 | AF3 플래그 기본값 |
| `sudo` 제거 (docker 그룹) | 매 건 sudo 호출 | 미미하지만 스크립트가 단순해짐 | - |

`--jax_compilation_cache_dir` 는 **단일 프로세스로 바꾼 뒤에** 의미가 생긴다
(다음 실행 배치에서 첫 컴파일을 줄이는 용도). 단독으로는 효과가 없다 — 단, 이는
#468 전제에 의존하는 주장이며 원문을 확인하지 못했다. 붙여도 손해는 없으니 붙여 쓰면 된다.

## 5. 2단계 분리의 알려진 함정 (반드시 읽을 것)

**[전달받은 전제]** 지시서가 공식 저장소 이슈 #485 를 출처로 제시한 내용:
데이터 파이프라인 단계와 추론 단계를 분리해서 실행하면
**unpaired MSA 누락으로 실패**하는 경우가 있다고 전해진다.
(이 트랙은 이슈 원문을 확보하지 못했다. 다만 아래 방어 코드는 전제가 맞든 틀리든
손해가 없는 종류의 검사이므로 그대로 넣었다 — 실패 원인을 컨테이너 실행 전에
한국어로 알려주는 것 자체가 이득이다.)

실무적 원인은 두 가지다.

1. `--norun_data_pipeline` 단계에 **원본 JSON을 그대로 넘긴 경우.**
   넘겨야 하는 것은 MSA 단계가 만들어낸 `<name>_data.json` 이다.
   원본에는 `unpairedMsa` 필드가 없으므로 즉시 실패한다.
2. **부분 지정.** AF3는 `unpairedMsa` / `pairedMsa` / `templates` 를
   일부만 채운 상태를 거부한다. 단량체라도 `pairedMsa` 는 빈 문자열 `""`,
   `templates` 는 빈 목록 `[]` 로 채워져 있어야 한다.

`af3_batch.py` 는 추론 단계 실행 **전에** 입력 파일을 검사해서 위 두 경우를
걸러내고 한국어 진단 메시지를 남긴다(`validate_data_json`).
검증기 단위 테스트 결과 **(측정: 스크립트 실행)**:

```
정상_MSA포함          -> 통과
원본JSON_MSA없음      -> 차단  "MSA 단계 산출물인 *_data.json 이 아니라 원본 JSON을 넘겼을 가능성"
pairedMsa_누락        -> 차단  "AF3 는 부분 지정을 거부한다"
templates_누락        -> 차단  "빈 목록 [] 이 들어 있어야 한다"
sequences_빈값        -> 차단
깨진JSON              -> 차단
```

또한 AF3가 입력 파일을 덮어쓸 수 있다는 언급(#488, 역시 전달받은 전제)이 있어,
`msa_store` 의 원본을 직접 마운트하지 않고 **복사본을 `stage_infer/` 로 넘긴다.**
MSA 산출물은 재계산이 아까운 자산이므로 보호한다.

## 6. 축소 DB에 대한 주의 (속도와 별개의 품질 문제)

축소 DB는 **속도에는 유리하지만 MSA 깊이가 얕아진다.**
VHH/나노바디는 프레임워크가 보존적이라 MSA가 얕아도 골격은 잡히는 편이지만,
CDR 루프의 신뢰도 지표(pLDDT)와 순위(ranking score)는 MSA 깊이에 영향을 받는다.

권고: **2단계 전략의 1단계(전수 스크리닝)는 축소 DB로 진행하되,
상위 후보를 최종 확정할 때는 더 큰 DB로 MSA를 다시 만들어 비교**할 것.
`af3_batch.py` 는 MSA를 `msa_store/` 에 분리 보관하므로,
DB를 바꿔 MSA만 다시 만들고 추론을 재실행하는 것이 쉽다.

`af3_check.sh` 5번 항목이 공식 DB 파일 목록과 대조해 무엇이 없는지 출력한다.
"없음"으로 나온 항목이 어느 검색 단계에 쓰이는지도 함께 찍는다.

## 7. 연구자 3개 질문에 대한 답 요약

**Q1. 왜 이렇게 느린가?**
건당 341초 중 **74~94%[추정]** 가 타깃 내용과 무관한 고정 오버헤드다.
JSON 하나마다 `docker run` 을 새로 띄워서 컨테이너 기동·JAX 초기화·가중치 로드·
XLA 컴파일을 760번 반복 지불했다. 특히 XLA 컴파일은 프로세스가 바뀌면
영구 캐시가 적중하지 않는다고 알려져 있다(#468 — 이 트랙이 원문을 확인하지 못한
전달받은 전제. 실측 트랙의 A/B가 이를 간접 검증한다).

**Q2. GPU를 더 사서/더 좋은 걸로 바꾸면 되는가?**
아니다. 지금 병목은 GPU 연산이 아니다. 5090을 더 빠른 카드로 바꿔도
①②③④ 는 거의 그대로 남는다. **스크립트 구조를 바꾸는 것이 하드웨어 교체보다
효과가 크고 비용이 0이다.** 예상 개선 5배 이상[추정].

**Q3. 한 번에 여러 개 돌릴 수 있는가?**
VRAM이 꽉 차 보이는 것은 JAX의 **선점** 동작이고 실사용량이 아니다.
선점을 끄면 실제 사용량을 볼 수 있고, 130 aa 단량체라면 여유가 있을 것이다.
그러나 **추론을 다중화해도 이득이 적다**(GPU 직렬화 + 오버헤드 중복 + OOM 위험).
정답은 "추론은 프로세스 1개로 전수 순회, 병렬화는 CPU MSA 단계에서".
